# E3 analysis — the conflicts are policy-level, and only the packaging text trips a guard

Raw: `raw/tag.jsonl` and `raw/plain.jsonl` (both instruments' stdout, verbatim)
and the scope partition of the same runs in `results-fixture.jsonl`; the rows
that share the verdict file's `real` scope are in `results.jsonl`.

## (a) The floating tag — CONFIRMED: 0 hits in bodies, 1 in the packaging text

| corpus | files | hits |
|---|---|---|
| upstream `skills/**/SKILL.md` (the suite's own corpus) | 38 | **0** |
| upstream every `.md` | 66 | **1** (`skills/in-progress/README.md`) |
| tezgah `skills/**/SKILL.md` (control) | 114 | 0 |

The install wording that `tests/test_skills.py:92` rejects is **not in a single
upstream `SKILL.md`**. The instrument walked `upstream` = `/tmp/mp-skills/skills`,
where the one hit is `skills/in-progress/README.md`; `.agents/install-block.md`
also carries `skills@latest` (lines 32, 44, 48) but sits outside every corpus
that run scanned - that half is a read of the fixture, not a row. So adopting
bodies alone does not touch that test;
carrying the surrounding documentation into a shipped skill does.

## (b) The attribution gate — CONFIRMED: the mandated line is allowed

`hooks/tezgah_gate.py:426` (`attribution`) read in process, scope `real`:

| command | denied |
|---|---|
| `gh issue comment 42 --body "> *This was generated by AI during triage.*"` | **False** |
| `gh issue create --title "x" --body "> *This was generated by AI during triage.*"` | **False** |
| `git commit -m "x\n\nCo-Authored-By: Claude"` (control) | True |

`gh issue comment` *is* a write command the rule reads
(`WRITE_CMD`, `hooks/tezgah_gate.py:180`, `GH_SUBCOMMANDS` includes `comment`),
and the control proves the rule is armed — the line simply does not match the
anchor set (`ATTRIB`, `hooks/tezgah_gate.py:151`: "generated **with**", not
"generated **by** AI").

**This is the finding that matters.** The pack's `triage` skill requires every
comment it posts to open with a generated-by-AI line
(`skills/engineering/triage/SKILL.md:15-17`), and tezgah's contract forbids AI
attribution on any host — yet **nothing that runs would stop it**. The conflict
is real, it is policy-level, and the mechanical rule is silent on exactly the
phrasing an adopted skill would use. Adopting that skill verbatim would publish
attributed comments while every gate stayed green.

## (c) The suite — CONFIRMED: the graft is inert, the text is not

| variant | baseline (clone at HEAD) | after grafting | failed |
|---|---|---|---|
| candidate body carrying `@latest` | pass | **fail** | `test_no_floating_npx_tag_and_the_fallback_names_the_wired_pins` |
| candidate body without it | pass | pass | — |

The grafted body is **synthetic** - a two-line `SKILL.md` the instrument writes,
not an upstream body - so the variant measures the float string's reach and
nothing about a real skill's shape. One test, exactly the one the predicate names. Both variants remain green
otherwise, so grafting a skill into `skills/` is itself inert: the suite goes red
because of the text, not the shape. This is the "see it fail once" check the
research contract asks for — the guard was observed firing, not merely asserted.

## What this does not show

- (b) is a statement about `attribution()` alone. Other rules in the same module
  (`secret_command`, `consent_effect`, `lang_reason`) were not exercised against
  the line; `attribution` is the one whose stated subject is AI credit.
- The suite probe ran `tests/test_skills.py` only, on a `git clone --local` of
  HEAD. The full discover suite was not run, so a second test failing on a
  grafted candidate elsewhere in the suite is not excluded.
- (a) counts the string, not the behaviour: a README that stays out of a shipped
  skill is not a conflict at all, and the pack's READMEs would not have to travel.
