# feature-audit · Ustam admin · users area

Method: `skills/feature-audit/SKILL.md` (read 2026-09-21), applied as written: five
layer-coherence matrices as tables, a coverage count per matrix, one Prevent line per
finding, and a capability-change proposal wherever a fix names a layer that does not
exist. Runtime half read from the repository's own committed artifacts (named per
finding) because this session was read-only on `apps/**` and had no running app.

## 0. Feature boundary

| | |
|---|---|
| Entity | A person together with their **membership** in the caller's organization (`User` + `Membership` + `MembershipRole`) |
| Actions | invite · change role · change scope · deactivate · reactivate · list/search/filter · view one |
| Screens | `apps/admin/app/(dashboard)/users/page.tsx` (list + filter + invite dialog + per-row edit dialog); no detail screen |
| Endpoints | `GET /users`, `GET /users/roles`, `GET /users/{id}`, `POST /users/invite`, `PATCH /users/{id}`, `POST /users/{id}/deactivate` |
| Server actions | `inviteUserAction`, `updateUserAction` (`app/(dashboard)/users/actions.ts`) |
| Service / storage | `apps/api/src/users/users.service.ts`; Prisma `User`, `Membership`, `MembershipRole`; outbox event `UserInvited` |
| Out of this boundary | mobile `OrganizationUsersScreen` (a *second surface* of the same feature, used below only as the sibling standard), `/teams` membership capacity, self-service profile |

Three passes ran, from different entry points:

1. **First-time operator** — the 390 px rendered screen
   (`apps/admin/test-results/artifacts/…-narrow-widths-chromium-admin/users-390.png`, written 2026-09-20 22:03) and the invite flow as the repository's e2e records it.
2. **Daily operator** — filter → edit → reload → re-filter, read from code plus the committed e2e assertions.
3. **API client with no UI** — the controller/service/outbox path, including the mobile client that consumes the same endpoints.

Evidence classes: `code` (path:line) · `ui-observed` (a named rendered read) ·
`behaviour` (an exercised action with its result) · `external` (a dated outside
standard) · `user-verbatim`. This artifact reports **no** `behaviour` and **no**
`user-verbatim` finding: nothing was exercised live (see §8).

## 6. Findings, most severe first

Severity is the skill's 0-4 scale over frequency × impact × persistence.

### 1 · An invitation reaches nobody: no delivery path exists — `code` — severity 3

- The invite writes the row with `status: 'ACTIVE'` and a hash of a random string that
  is then discarded: `users.service.ts:116` (`hashPassword(this.randomInvitePassword())`),
  `:323-325`, `:118-127`.
- The only consumer of the `UserInvited` event is the push handler
  (`users.service.ts:168-174` → `worker/push-notification.handler.ts:73-74`), and its
  recipient resolution is the just-created user `:134-135`, who cannot have a registered
  device. No e-mail path exists for invitations: the repository's only mail provider is
  `PasswordResetEmailProvider` (`apps/api/src/auth/auth.module.ts:11`,
  `password-reset-email.provider.ts:9-11`).
- The fallback activation route (self-service password reset, `app/forgot-password/`)
  is off by default — `PASSWORD_RESET_EMAIL_PROVIDER` defaults to `disabled`
  (`packages/config/src/index.ts:262`), and when it is disabled the request throws
  `PASSWORD_RESET_DELIVERY_UNAVAILABLE` (`password-reset-email.provider.ts:14,41-47`).
- The surface says only "Takım daveti oluşturuldu." (`MutationNotice.tsx:45`) — true, and
  silent about there being no recipient.
- Not a `behaviour` claim: I could not exercise a real invite, and no deployment
  environment was inspected, so the "disabled by default" half is a configuration
  citation, not a running-system observation.
- **Prevent**: a contract test over the outbox event registry asserting every
  `User*` lifecycle event has a handler that resolves a *reachable* channel for a user
  with no session, plus an e2e that asserts the invited address received an activation
  message through a stub mail sink. That check fails today on both halves.

### 2 · The role picker offers `SUPER_ADMIN`, which both write paths refuse — `code` — severity 3

- Surface: both selects map the server's whole role list (`page.tsx:113-117`, `:251-255`;
  source `users.service.ts:69-73`).
- The same feature refuses that value twice: `actions.ts:61` and `:87`, and the service
  refuses it at the domain boundary (`users.service.ts:336-349`,
  `SUPER_ADMIN_PROVISIONING_REQUIRED`).
- That the option is genuinely offered in the running app is recorded by the
  repository's own e2e, which asserts the offered set equals
  `['ORG_ADMIN','SUPER_ADMIN','TECHNICIAN']` (`e2e/admin-core-recovery.e2e.ts:118-127`).
- Sibling standard, both sides cited: mobile's screen offers six roles
  (`OrganizationUsersScreen.tsx:28-35`), its API type excludes the value
  (`organization-users-api.ts:35`), and a contract test holds it there
  (`organization-users-role-boundary.contract.test.ts:7-17`).
- The unit fixture hides the defect: `page.test.tsx`'s `orgRoles` omits `SUPER_ADMIN`,
  so the offered-set assertion passes on a list production never returns.
- **Prevent**: add `/users` to the persisted offered-role boundary contract (the mobile
  pattern) — an assertion that no `select[name="roleKey"]` ever offers an unassignable
  key, driven by `assignableRoleKeys(orgRoles)`, not by a hand-written fixture.

### 3 · The invitee is written `ACTIVE`, so an unaccepted invitation and an established member look identical — `code` — severity 3

- Written state: `users.service.ts:127` — the create always sets `ACTIVE`; nothing
  anywhere writes `INVITED` (search in §8, coverage limit stated there).
- Offered labels: `userStatusLabels` carries five keys (`user-labels.ts:16-22`) while
  the enum has four (`apps/api/src/generated/prisma/enums.ts:53-58`): `DEACTIVATED` and
  `DELETED` label values that do not exist, `ARCHIVED` exists and has no label and is
  filtered out of the list anyway (`users.service.ts:30`).
- Both the label map and the notification copy anticipate the missing state —
  `userStatusLabels.INVITED = 'Davet edildi'` `user-labels.ts:18`,
  `pushNotificationCopy.UserInvited = 'ServisTek daveti'`
  `worker/push-notification.handler.ts:74`.
- Consequence: neither the operator nor the state filter can separate "invited, never

### 4 · At 390 px five columns and every row action sit outside an undiscovered scroll, and the e-mail column is clipped mid-value — `ui-observed` — severity 3

- Read: `apps/admin/test-results/artifacts/admin-foundation.e2e.ts-al-f1f5c-t-desktop-and-narrow-widths-chromium-admin/users-390.png`
  (390 CSS px viewport, light theme, full-page; file written 2026-09-20 22:03). In that

  `Kapsam`, `Üyelik` and `Yetki güncelle` — including every row's "Erişimi düzenle"

- Mechanism: `th,td{white-space:nowrap}` `globals.css:568-574` inside

- Why the existing checks pass: the suite asserts *document* overflow

### 10 · The invite mutation has no idempotency contract, and one client already sends a key the route ignores — `code` — severity 2

- **Prevent**: a route-parity test asserting `/users/invite` honours `Idempotency-Key`
