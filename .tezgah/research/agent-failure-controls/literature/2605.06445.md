### 2. How This Work Fits into the Broader Research Landscape

The field of Large Language Model (LLM) agents for autonomous code generation has experienced rapid advancements. Existing literature and benchmarks, such as those related to SWE-Bench, OpenHands, and SWE-Agent, demonstrate LLM agents' capabilities in "shallow" generation tasks, including rapid prototyping, demo applications, frontend interfaces, and resolving GitHub issues. These tasks often involve loosely defined objectives where structural decisions can be largely delegated to the agent. Benchmarks typically focus on functional correctness, often through unit tests or end-to-end behavioral tests, or on single-file solutions and code completion. Some recent efforts have explored greenfield application generation or issue resolution within existing codebases.

However, a gap exists in the evaluation of LLM agents' performance under strict structural constraints, which are inherent to production-grade software development. Real-world backend systems require adherence to architectural patterns (e.g., Clean Architecture), integration with specific database backends (e.g., PostgreSQL, SQLite), and the use of designated Object-Relational Mappers (ORMs) (e.g., SQLAlchemy, Sequelize). These non-functional requirements are critical for maintainability, scalability, and integration within enterprise environments but have not been systematically investigated in current benchmarks.

This research addresses this gap by conducting a systematic study specifically designed to evaluate LLM agents in multi-file backend generation tasks that mandate adherence to various structural constraints. By isolating the impact of these constraints, the work aims to provide insight into the fragility of LLM agents in scenarios demanding both functional correctness and structural compliance, thereby extending the understanding of their capabilities beyond loosely specified tasks. It also explores the influence of different web frameworks and identifies common root causes of failure when these constraints are introduced.

### 3. Key Objectives and Motivation

The primary motivation for this research stems from the observation that while LLM agents show considerable promise in autonomous code generation, their performance in producing production-grade backend software under strict, real-world development constraints remains largely unexamined. Current benchmarks often reward solutions that are functionally correct but structurally arbitrary, neglecting the non-functional requirements vital for deployable software.

The key objectives of this study are:

1.  **Systematic Evaluation of Structural Constraint Handling**: To conduct a systematic study assessing how well LLM agents handle structural constraints in multi-file backend generation. This involves moving beyond loosely specified tasks to scenarios where explicit architectural patterns, database choices, and ORM integrations are mandated.
2.  **Quantification of Performance Degradation (Constraint Decay)**: To measure the decline in agent performance as the density of non-functional structural constraints increases. The researchers hypothesize a phenomenon termed "constraint decay," where performance significantly degrades when moving from unconstrained generation to fully specified systems.
3.  **Isolation of Constraint Effects**: To design an experimental methodology that isolates the effect of structural constraints from the functional complexity of the task. This is achieved by fixing a unified API contract across all tasks and deploying a shared suite of end-to-end behavioral tests, thereby allowing for controlled, equitable comparisons.
4.  **Analysis of Framework Sensitivity**: To investigate whether the choice of web framework significantly influences an agent's success when generating code under identical API contracts and increasing structural constraints. This aims to identify potential disparities in agent performance across different framework paradigms (e.g., minimal vs. convention-heavy).
5.  **Identification of Root Causes of Failure**: To perform an extensive error analysis to identify the primary root causes of agent failures in constrained backend generation tasks. This objective seeks to pinpoint specific areas where LLM agents struggle, such as data-layer interactions, architectural adherence, or framework-specific nuances.

By pursuing these objectives, the research aims to highlight that jointly satisfying both functional and structural requirements represents a significant open challenge for LLM coding agents, thereby informing future research directions and development efforts.

### 4. Methodology and Approach

The research employs an evaluation methodology inspired by Behavior-Driven Development, designed to hold the functional specification constant while systematically varying non-functional structural requirements.

**4.1. Generation Task Design**
*   **Greenfield Generation Tasks**: Agents are tasked with generating a complete, specification-compliant REST API from an empty repository.
*   **Input Prompt Components**: Each agent receives a prompt with four components:
    1.  **API Specification**: The OpenAPI 3.0 specification is used as a standardized, machine-readable format to define functional requirements (endpoints, schemas, request/response bodies, status codes), reducing ambiguity and enabling pre-definition of a behavioral test suite. The specification is derived from the RealWorld Conduit API, encompassing 19 CRUD operations across five resource groups. A single, fixed API contract is used to maximize internal validity.
    2.  **Structural Constraints**: Details on architectural patterns, database, and ORM requirements.
    3.  **Mandatory Files**: Required files for code execution (e.g., `requirements.txt`, `run.sh`).
    4.  **Evaluation Pipeline Description**: Information on how the submission will be assessed.
*   **Framework Coverage**: Eight popular web frameworks are included as an experimental factor: Flask, FastAPI, Django, aiohttp (Python 3.12) and Express, Fastify, Hono, Koa (Node.js 20).

**4.2. Constraint Dimensions**
Three orthogonal non-functional axes are defined and systematically layered to create task variants:
*   **Architectural Pattern**: Mandates adherence to the Clean Architecture pattern (Martin, 2017), requiring the codebase to be organized into four domain layers (routes/handlers, services/use cases, models/entities, repository/data access), each in its own directory, with strict top-down dependency direction.
*   **Database Backend**: Requires data persistence using either PostgreSQL (a pre-configured instance is provided) or SQLite (no external service needed), with automatic schema creation at server startup.
*   **ORM Integration**: Specifies the use of a particular ORM (SQLAlchemy for Python, Sequelize for Node.js), requiring idiomatic query logic instead of raw SQL.
*   **Constraint Levels (L0-L3)**: The web framework is always specified (baseline constraint). The other three dimensions are systematically composed into task variants of increasing specification density:
    *   **L0**: Web Framework only (baseline).
    *   **L1**: WF + one additional constraint (e.g., WF + Architecture).
    *   **L2**: WF + two additional constraints (e.g., WF + Architecture + SQLite).
    *   **L3**: WF + all three constraints (e.g., WF + Architecture + PostgreSQL + ORM).
    This generates 80 greenfield generation tasks (8 frameworks × 10 constraint combinations).

**4.3. Evaluation Pipeline**
Each task is executed in an isolated Docker environment with two phases:
*   **Build Phase**: The LLM agent operates in a container to code, build, and start the server.
*   **Evaluation Phase**: The agent's generated code is applied in a pristine container, and the behavioral test suite is executed. An ephemeral PostgreSQL 16 instance is available in both phases.
*   **Behavioral Testing**: A unified HTTP behavioral test suite, comprising 32 requests covering all 19 API endpoints and 291 assertions (verifying response structure, types, status codes, and state transitions), is used for evaluation. This suite is decoupled from internal code structure.
*   **Verifier Functions**: Orthogonal static verifier functions assess structural compliance:
    *   **Architecture Verifier**: Checks for the presence of at least three out of four canonical Clean Architecture layers and verifies top-down dependency direction from import statements.
    *   **Database Verifier**: Scans source lines for evidence of the prescribed database engine (e.g., `sqlite3` imports, `postgresql://` connection strings) and absence of alternatives.
    *   **ORM Verifier**: Detects usage of the designated ORM (e.g., `import sqlalchemy`) without penalizing alternative ORMs if not actively used.
*   **Task Success**: Defined as the intersection of passing the entire behavioral test suite and satisfying all applicable verifier functions.

**4.4. Experimental Setup**
*   **Metrics**: Assertion Pass Rate (A%) – mean fraction of behavioral test assertions passed, capturing partial progress. Pass@k (pass@1) – probability of at least one of *k* samples satisfying all constraints. A% is the primary metric.
*   **Trials**: `n=3` independent trials per agent-model configuration.
*   **Agents**: Two open-source agent architectures: Mini-SWE-Agent (minimal, bash-based) and OpenHands (full-featured, dedicated tools).
*   **Models**: Four tiers: Small open agentic (Devstral-Small, Qwen3-Coder-Next), Large open instruct (Qwen3-235B-Instruct), Large open agentic (MiniMax-M2.5, Kimi-K2.5), and Closed models (GPT-5-mini, GPT-5.2).
*   **Cost-Driven Evaluation Scope**: Due to high token consumption, high-cost models (Kimi-K2.5, GPT-5.2, MiniMax-M2.5) were evaluated on a representative 16-task subset (4 frameworks × 4 constraint levels), which was validated for representativeness against full-set configurations.
*   **Agent Adjustments**: System prompts for Mini-SWE-Agent were realigned for generative tasks, and a re-prompting mechanism was implemented for OpenHands to mitigate premature halting.

**4.5. Feature Implementation Tasks (Sanity Check)**
*   **Design**: 20 tasks created by ablating specific feature groups (e.g., "comments") from community-maintained RealWorld repositories that already embed L3-like constraints (layered architecture, PostgreSQL, ORM).
*   **Purpose**: To verify if "constraint decay" is unique to greenfield generation or persists when agents must infer and respect constraints from an existing codebase. Agents must re-implement missing functionality.

### 5. Main Findings and Results

The study yielded several findings regarding the performance of LLM agents in constrained backend code generation.

**5.1. RQ1: Effect of Constraint Accumulation**
*   **Constraint Decay Phenomenon**: A substantial and universal decline in agent performance was observed as structural constraints accumulated. For capable configurations (those exceeding 50% A% at L0), the assertion pass rate (A%) dropped by an average of 30 percentage points (a 40% relative loss) from the unconstrained baseline (L0) to fully specified tasks (L3). Some configurations approached zero A% at L3.
*   **Baseline Performance**: Without structural constraints (L0), models like Qwen3-Coder-Next, MiniMax-M2.5, and Kimi-K2.5 demonstrated A% scores exceeding 85%, indicating proficiency in unconstrained backend generation. Smaller or non-specialized models struggled even at L0.
*   **A% vs. Pass@1**: A consistently large gap was noted between A% and pass@1. Even the strongest L3 configuration achieved 78.6% A% but only 8.3% pass@1, indicating that while agents often achieve partial functional correctness, full compliance across all assertions and constraints is rare, suggesting a lack of cross-file consistency.
*   **Scaffold Effect**: The choice of agent scaffold (Mini-SWE-Agent vs. OpenHands) had a measurable impact on performance, with OpenHands outperforming Mini-SWE-Agent for some models (GPT-5-mini, MiniMax-M2.5) but not others (Qwen3-Coder-Next). However, the trend of constraint decay remained consistent across both.
*   **Per-Constraint Analysis**:
    *   Specifying a **database engine** (PostgreSQL or SQLite) was identified as the most impactful constraint, causing an average A% drop of 19.3 points for PostgreSQL and 14.3 points for SQLite.
    *   Enforcing **Clean Architecture** resulted in a significant penalty, with an average A% drop of 9.1 points.
    *   **ORM integration** (SQLAlchemy, Sequelize) showed a smaller average A% drop (1.5 for SQLAlchemy, 0.6 for Sequelize), and for some models, it even improved performance by making data-access patterns more explicit.
*   **Verifier Impact**: The inclusion of static verifier functions for structural compliance had a negligible impact on the overall A% scores and the observed decay signal (at most 2.7 percentage points difference), indicating that functional failures, rather than verifier false negatives, drove the constraint decay.
*   **Feature Implementation Tasks**: In a sanity check involving 20 tasks requiring agents to add features to existing, constrained codebases, performance remained low (only GPT-5.2 exceeded 50% pass@1). This indicated that the challenges observed in greenfield generation are not artifacts of starting from scratch but persist when agents must infer and respect existing structural constraints.

**5.2. RQ2: Framework Sensitivity**
*   **Performance Disparities**: Significant performance disparities were observed across the eight web frameworks, even under identical API contracts and evaluation conditions.
*   **Top Tier**: Lightweight and explicit frameworks like Express, Koa, and Flask formed a top tier, achieving average A% scores of 51.4%, 50.7%, and 49.3% respectively. These frameworks typically have minimal implicit conventions.
*   **Lower Tier**: Convention-heavy environments such as Django and FastAPI performed substantially worse, trailing by 25–32 percentage points compared to the top tier. This penalty is attributed to their implicit configurations and type-hint-driven validation.
*   **Hono.js Performance**: Hono.js also trailed, despite its comparable API surface to Express, potentially due to its target edge runtimes and the requirement for a compatibility adapter on Node.js, which might be underrepresented in LLM training data.

**5.3. RQ3: Root Causes of Failure**
A failure analysis performed on Qwen3-Coder-Next and MiniMax-M2.5 with Mini-SWE-Agent identified the following:
*   **Coarse Failure Categories**:
    *   **Logic errors** accounted for approximately 71% of failures for both models, indicating that the server typically started and registered routes but exhibited incorrect behavior. This aligns with the large gap between A% and pass@1.
    *   **Server startup failures** were the second most common category, ranging from 12% to 21%.
    *   Other categories (incomplete implementation, schema/format errors, stuck in loop, constraint violation) accounted for less than 17% combined.
*   **Logic Error Sub-Categories**:
    *   **Data-layer defects** were identified as the leading root causes, collectively accounting for a significant portion of logic errors. These included:
        *   **Incorrect query logic**: SQL queries executing but returning wrong results due to incorrect joins, filters, or dialect-incompatible operators (25.5% for Qwen3-Coder-Next, 15.0% for MiniMax-M2.5).
        *   **DB/ORM runtime errors**: Conceptually correct query logic crashing due to misuse of ORM APIs (21.2% for Qwen3-Coder-Next, 15.0% for MiniMax-M2.5).
    *   **Auth misconfiguration** was a notable model-specific weakness for Qwen3-Coder-Next (22.6% vs. 5.0%), primarily due to incorrect token-prefix parsing.
    *   **Framework idiosyncrasy** was significant for MiniMax-M2.5 (50.0%), mainly attributed to Fastify's rejection of empty-body POST requests.
    *   Other logic errors included business logic defects and state propagation failures.
*   **Data-Layer Difficulty**: The prevalence of data-layer defects confirmed that database constraints impose a steep penalty. This is consistent across scenarios, manifesting as ORM runtime errors when ORM constraints are active, and as raw SQL errors when they are not, indicating the intrinsic difficulty of correctly interfacing with the data layer.

### 6. Significance and Potential Impact

This research systematically identifies and quantifies "constraint decay," a phenomenon where the performance of LLM-based coding agents substantially degrades when faced with explicit structural requirements in backend code generation. This finding has several implications for the development and application of LLM agents in software engineering:

*   **Refined Understanding of Agent Capabilities**: The study refines the understanding of LLM agents' capabilities, indicating that while they are proficient in generating functionally correct code under loose specifications (e.g., for rapid prototyping or demo applications), their reliability diminishes significantly when production-grade structural constraints are imposed. This clarifies that current agents are not yet suitable for autonomous production-grade backend development without substantial human intervention.

*   **New Benchmarking Imperatives**: The work highlights the limitations of existing benchmarks that primarily focus on functional correctness. It argues for a shift towards evaluation methodologies that actively integrate structural awareness and compliance, encouraging the development of benchmarks that capture the complexities of real-world software engineering requirements. The open-sourced evaluation pipeline, task suite, and analysis scripts provide a resource for this evolution.

*   **Direction for Agent Development**: The identified root causes of failure, particularly data-layer defects (incorrect query composition, ORM runtime violations) and framework sensitivity, provide concrete directions for future agent development. Agent developers can focus on enhancing LLMs' understanding of:
    *   **Architectural Patterns**: Incorporating mechanisms for planning and adhering to complex, multi-file architectural structures.
    *   **Database Interactions**: Improving the ability to correctly compose queries, manage database schemas, and handle ORM-specific idioms and potential runtime errors.
    *   **Framework Nuances**: Developing strategies for better adaptation to framework-specific conventions, configurations, and idiosyncrasies, particularly in convention-heavy environments. This could involve retrieval-augmented generation from framework documentation or targeted pre-training.

*   **Impact on Software Engineering Practices**: For software practitioners, the findings suggest that while LLM agents can accelerate initial development phases, their outputs still require thorough validation against structural requirements. It underscores the ongoing necessity for human oversight in ensuring code quality, maintainability, and adherence to established engineering standards for mission-critical applications.

In summary, this research contributes to a more nuanced understanding of LLM agents' performance boundaries in complex code generation, guiding the community towards developing more robust and structurally aware AI-powered software development tools.
