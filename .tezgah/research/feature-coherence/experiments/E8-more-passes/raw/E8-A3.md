## Boundary (the unit)

- **Entity**: a user plus their organization membership (role set, record scope, active flag).
- **Actions**: list/filter the user set; invite a user; change a user's role / scope / active flag;
  reactivate an inactive membership; read one user's full membership (server-side only);
  deactivate a membership (server-side route, no panel caller).
- **Screens**: `app/(dashboard)/users/page.tsx` only — no detail screen, no wizard.
- **Endpoints**: `GET /users`, `GET /users/roles`, `GET /users/:id`, `POST /users/invite`,
  `PATCH /users/:id`, `POST /users/:id/deactivate`.
- **Files**: `apps/admin/app/(dashboard)/users/{page.tsx,actions.ts,user-labels.ts}`,
  `apps/admin/components/{AdminActionForm,AdminModal,ConfirmationDialog,MutationNotice,PageHeader}.tsx`,
  `apps/admin/lib/{api,mutations,mutation-guard,admin-context,admin-surfaces}.ts`,
  `apps/api/src/users/{users.controller,users.service}.ts`, `packages/domain/src/users.ts`,
  `apps/api/prisma/{seed,seed-role-permissions}.ts`.

Surfaces in scope: the invite modal (2 text fields, 2 selects, confirm dialog), the filter toolbar
(1 input, 1 select, 2 controls), the 7-column table (rows, badges, one action cell with 4 shapes),
the count line, the empty state, the per-row edit modal, the page-level locked surface.

**What produced evidence, and what did not.** One pass ran, and it was a source pass: I read the
layers above and executed one expression outside the app (F7). **No running app, no browser, no
axe-core, no rendered pixels, no live response, no database.** The skill asks for three passes from
different entry points; this run is one, so every `ui-observed` row below is absent by construction,
not by finding. Per-finding coverage is in §8.

Severity: 0–4 = frequency × impact × persistence, from the citations only.

## 6. Findings, most severe first

Each: severity, evidence class, citation, and the cheapest thing that stops the family returning.

### F1 — The invite picker offers a role both the action and the service refuse (severity 3)
**Evidence class: `code`.** `GET /users/roles` returns every role bound to the caller's
organization (`users.service.ts:69-74`, no assignability filter), and the page renders all of them
as options, defaulting to `TECHNICIAN` when present and otherwise to `roles[0]`
(`page.tsx:106-118`). `SUPER_ADMIN` is in the accepted enum (`domain/users.ts:14-22`) and is refused
twice: the action short-circuits before the API call (`actions.ts:61`) and the service refuses it
(`users.service.ts:114` → `:322-325`). The panel's own session requires `SUPER_ADMIN` inside a
`kind = PLATFORM` organization (`auth/admin-panel.guard.ts:30-43`, `admin-panel-session.ts:11-13`),
and the demo seed defines exactly one role in that organization: `SUPER_ADMIN`
(`seed-role-permissions.ts:64-71`). So in the panel's own organization the only selectable role is
the refused one, and the invite cannot complete there; production platform organizations may define
more roles, but nothing filters the option set by assignability. Three more faces of the same gap:
(a) the label for that key comes from two sources that disagree in the same rendering path —
`roleLabels['SUPER_ADMIN'] = 'Platform sahibi'` (`user-labels.ts:2`) wins over the server's
`Platform Sahibi` (`seed-role-permissions.ts:69`) via `?? role.name` (`page.tsx:115`); (b) the
mobile client forbids the same option by type and by contract test — `Exclude<Role,'SUPER_ADMIN'>`
(`organization-users-api.ts:36`) held by a test that asserts the screen never offers it
(`organization-users-role-boundary.contract.test.ts:8-20`) — the panel has no equivalent, and its
page test mocks a tenant-shaped role list (`page.test.tsx:24-28`), which is why it passes;
(c) the e2e this screen owns drives `selectOption({label: 'Teknisyen'})`
(`e2e/admin-core-recovery.e2e.ts:18-22`) against a seeded panel organization that has no such role —
**[NOT CHECKED: e2e suite not run; its setup signs in as `admin@servistek.test`, which `seed.ts:165-168`
seeds as an ORG_ADMIN of a tenant organization, not the platform owner, so whether it reaches `/users`
at all is unverified]**.
**Prevent:** filter the endpoint to assignable keys server-side AND add the assertion the mobile
already has, on the panel side: `expect(roles.map(r => r.key)).not.toContain('SUPER_ADMIN')` in
`page.test.tsx` against a platform-shaped role fixture, plus a contract test that every key
`GET /users/roles` returns survives `InviteUserInput.safeParse` for a non-platform actor. That test
fails on today's fixture and on the seeded platform organization.

### F2 — The invite produces an account nobody can enter (severity 3)
**Evidence class: `code`.** The invited user is created with a random password that is hashed and
never returned (`users.service.ts:116`, `:323-325`) and `status: 'ACTIVE'` (`:127`), and the only
outbox event is `UserInvited` (`:172-173`), whose sole handler is the push notifier
(`worker.module.ts:108-113` maps `notificationEventTypes` to `PushNotificationOutboxHandler`;
`push-notification.handler.ts:74` gives it the copy `'ServisTek daveti'`). Its recipient is
`event.aggregateId` — the brand-new user (`push-notification.handler.ts:134-135`), who by
construction has no device push token: a token is registered after sign-in
(`devicePushToken` is what `revokeMembershipAccess` deactivates, `users.service.ts:282-296`). The
system does have an email channel (a password-reset email provider exists) and the invite does not
use it. The invite is also invisible as a product event: `adminApi` emits `create.started` only for
`/customers` and `/work-orders` (`lib/api.ts:46-52`), so `POST /users/invite` produces no create
event pair. **Prevent:** an integration test that fails today — after `usersService.invite`, assert
an `outboxEvent` exists whose `eventType` is handled by a delivery handler that is not push-only;
plus a check that every event type in `notificationEventTypes` has a non-push delivery path or a
documented reason. Without a delivery assertion this regresses every time the notification surface
changes.

### F3 — Deactivation revokes sessions and devices silently (severity 2)
**Evidence class: `code`.** `PATCH` with `active:false` calls `revokeMembershipAccess`, which
deactivates push tokens, revokes refresh sessions and revokes device activations
(`users.service.ts:179-244`, `:275-296`) and emits **no** outbox event — the transaction records an
audit row and nothing else (`:236-241`). The sibling path in the same codebase does announce it:
revoking a device session emits `SessionRevoked` (`devices.service.ts:196-199`), and profile/security
changes emit `AccountSecurityChanged` (`me.service.ts:54-57`, `:254-257`). The affected person is
never told, and the confirmation copy that promises the effect (`page.tsx:237`) is the only surface
that ever says it.
**Prevent:** a test on `UsersService` asserting that any transition to `active:false` writes an
outbox event whose type maps to a notification (`notification-event-mapper.ts`), mirroring the
device-revoke assertion. Cheapest mechanical form: extend the existing
`integration/profile-security-lifecycle.test.ts` shape with a membership-deactivation case.

### F4 — A capability the server has and no panel user can reach: the user detail (severity 2)
**Evidence class: `code`.** `GET /users/:id` returns the full membership including role names
(`users.controller.ts:49-57`, `users.service.ts:77-110`) and no screen in `apps/admin` calls it —
the search for `/users` over `apps/admin` returns only `/users`, `/users/roles`, `/users/invite` and
`/users/${id}` in `actions.ts:89`, a PATCH. The list shows a truncated view: roles joined into one
cell (`page.tsx:192-196`), no role names, no locale, no membership id. The row's only action is an
edit dialog, so "who is this person, exactly?" has no surface. Related: the repo's own CRUD coverage
registry enumerates 10 surfaces with their operations and does not include `/users`
(`lib/admin-crud-coverage.ts`; the test at `lib/admin-crud-coverage.test.ts` only walks that
list), so the existing reachability contract never asks the question for this surface.
**Prevent:** add a `/users` row to `adminCrudCoverage` with `operations: ['create','read','update']`
and the mutations `['team.invite','team.update']`; the existing test then fails if the read
operation loses its surface. This is the cheapest check that turns "no surface calls this" into a
failure instead of a review habit.

### F5 — Two routes for one action, and the audit trail depends on which caller used it (severity 2)
**Evidence class: `code`.** `PATCH /users/:id` with `active:false` records `user.update`
(`users.service.ts:237`) with `redactedDiff:{changed:['active']}` `:240`, and the panel's audit
screen labels that `'Kullanıcı bilgisi güncellendi'` (`audit/audit-model.ts:84`). The dedicated
`POST /users/:id/deactivate` records `user.deactivate` (`users.service.ts:268`), which the audit
label map does not contain (`audit-model.ts:83-84` jumps `user.invite` → `user.update`), and which
no client calls at all. So the deactivation an operator performs is recorded — and read back — as a
generic update, while the route that names it correctly is dead.
**Prevent:** a route-inventory contract test over `UsersController` asserting every declared route
has a caller in `apps/admin` or `apps/mobile` (or is listed as panel-internal), and, for the audit
side, a test that every `action` string passed to `AuditService` has a label in `audit-model.ts`.
Both are list-vs-code checks and both fail today.

### F6 — The filter runs in memory under a pagination envelope nobody computes (severity 2)
**Evidence class: `code`.** The API returns `page:{nextCursor:null,hasNextPage:false}` as a literal
(`users.service.ts:64`) with no query parameters accepted (`users.controller.ts:34-38`), and the
page parses only `data`, dropping the envelope (`page.tsx:13-27`, `:58`). The filter and the state
facet run over the full array in the server component (`:60-66`) after fetching every user. The
count line then states a total from that single response — `"{allUsers.length} kullanıcıdan
{users.length} kayıt gösteriliyor"` (`:164`) — which is a claim about the whole tenant that no
pagination ever verifies. The sibling convention is the opposite: the audit screen parses the same
envelope and paginates on it (`audit/page.tsx:14-28`), and other endpoints in the API compute real
signed cursors. **Prevent:** a contract test that every list response consumed by the panel either
carries a computed `page` or omits the key — i.e. assert `hasNextPage === false` only when the query
is unbounded, or delete the key. The assertion that would have failed is the honest one: a seeded
organization with more users than the request can return must show `hasNextPage: true`.

### F7 — Turkish casefold: an uppercase-ASCII name cannot be found by typing it in lowercase (severity 2)
**Evidence class: `behaviour`.** Executed the exact filter expression from `page.tsx:60-66` outside
the app (`node v22.23.1`, full ICU), on rows shaped like the API response: query `"ilkay"` returns
`[]` for a row whose `displayName` is `"ILKAY Demir"`, while `"ILKAY"` and `"ılkay"` both match;
`"iLkAy"` returns `[]` too (`'I'.toLocaleLowerCase('tr-TR') === 'ı'`). The dotted-İ direction is
correct (`"ipek"`, `"İPEK"`, `"İpek"` all match `İpek Yılmaz`), so this is a real Turkish-locale
miss, not a general case bug. Note this was observed on the expression, **not** in the browser —
**[NOT CHECKED: no running app]**. The codebase already owns the primitive for the fix: customers
and directory rows store `normalizedSearchName` built by `normalizeTurkishSearch` (`seed.ts:532,544`)
and search on it; the user list has no such column and filters the raw strings.
**Prevent:** a table-driven unit test over the seed's own names — the demo data contains `İpek Işık`
(`seed.ts:532`) — asserting that a row is found by its ASCII transliteration; the durable form is a
normalized search column on the user query, at which point the assertion moves to the query.

### F8 — `locale` is carried by the contract and rendered nowhere (severity 1)
**Evidence class: `code`.** The API selects and returns it (`users.service.ts:26-66` list projection, `:77-110` detail), the
page declares it (`page.tsx:20`), and no surface prints it; the one sentence that mentions language
tells the operator the user changes it in their own profile (`:164-165`), and this app has no
profile surface (`grep -n "profile" apps/admin/lib/admin-surfaces.ts apps/admin/app apps/admin/components`
returns only unrelated audit actions and a campaign placement enum). The field is not wrong to
carry — it is a field with no view, and the copy points at a surface outside this panel.
**Prevent:** a field-contract test over the `/users` response schema asserting every field is either
rendered by a surface or listed in an explicit exclusion set with a reason. That assertion fails
today for `locale` and for the dropped `page` envelope (F6), which is the point.

### F9 — The status label map describes states the system cannot produce (severity 1)
**Evidence class: `code`.** `userStatusLabels` has five keys (`user-labels.ts:16-22`) for a
four-value Prisma enum (`schema.prisma:39-43`): `DEACTIVATED` and `DELETED` have no enum value and
no writer anywhere; `INVITED` has a label but no writer either — the invite path writes `ACTIVE`
(`users.service.ts:127`), verified by a search for `'INVITED'` across `apps/api/src` that returns
only the generated enum and the Prisma enum; and `ARCHIVED` is excluded from the list query
(`users.service.ts:26-31`), so it can never render either. In one row two columns then print the same
word for two different facts: `Durum` = `Aktif` from the global user status (`page.tsx:186-190`) and
`Üyelik` = `Aktif` from the per-organization membership (`:200`), so a user invited a second ago
reads as "Aktif" in a column that means "this account can sign in".
**Prevent:** generate the label record from the enum (`Record<UserStatus, string>` over the Prisma
type rather than a free `Record<string,string>`) so an unreachable key is a type error, and assert in
the page test that the two columns never render the same string for a row whose `status !== 'ACTIVE'`.

### F10 — The error copy promises a mark nothing styles, and the summary may not be the only mechanism (severity 1)
**Evidence class: `code`.** Two cited sides. The action's summary line says the marked fields must be
corrected — `'Alanları kontrol edin. İşaretlenen bilgileri düzeltip yeniden deneyin.'`
(`actions.ts:22`) and the component repeats `'İşaretli alanları düzeltin.'`
(`AdminActionForm.tsx:281`) — while the only mark applied is an attribute: `aria-invalid="true"`
plus an `aria-describedby` pointing into the summary list (`:99-102`), and `globals.css` contains no
`[aria-invalid]` rule (grep over `apps/admin/app/globals.css` and `apps/admin/components` returns no
styled selector). The second half: the form does not suppress native validation, so the browser's own
invalid bubble is not disabled, yet the component's comment states the summary replaces that second
mechanism (`:41-43`) — **[NOT CHECKED: needs a browser; jsdom cannot produce the bubble, and no
running app was available to this pass]**. Also note the sub-case the same mechanism handles well:
the summary entry is a button that focuses its field, which is asserted in
`AdminActionForm.test.tsx:159-163`.
**Prevent:** add the `[aria-invalid='true']` style rule (or change the copy to name the summary
instead of a mark) — a one-line CSS contract; and for the bubble, no mechanical prevention exists
without `novalidate`, so it stays a review item until this pass can be repeated in a browser.

### F11 — The table is a table of tab stops (severity 1)
**Evidence class: `code`.** Every row's action cell holds a focusable control — one dialog trigger or
one submit button (`page.tsx:201-282`) — so a 30-row list is 30+ tab stops between the filter and the
footer, which is the pattern the grid rule exists to avoid. The file's own comment argues the
opposite trade ("Per-row edit opens as its own dialog: the table stays a table", `:223`), which is
true about the *screen* and false about the *keyboard*.
**Prevent:** no mechanical prevention exists for the one-tab-stop rule without adopting the grid
pattern; the cheap assertion is a keyboard e2e that counts the tab stops per row (exactly 1 today),
so a future second per-row control fails a test instead of a review.

### F12 — A field error lands on a surface the operator can no longer see (severity 1)
**Evidence class: `code`.** The invite's server action can return field errors (e.g. `ROLE_NOT_FOUND`
→ `roleKey`, `actions.ts:29-32`), and `AdminActionForm` writes those into the form's summary and
`aria-describedby` (`:92-112`, `:284-299`). When the submitted form came from a modal, the
confirmation dialog closes on submit (`ConfirmationDialog.tsx:96-103`) and the modal stays open, so
the summary is rendered inside the dialog — reachable. The failure mode is the redirect path instead:
on success the modal closes, and on the *next* open the form still holds the previous values
(nothing resets the DOM after a successful operation; only the idempotency map is cleared,
`AdminActionForm.tsx:191-197`), so a repeat invite re-submits identical data and lands on the
`ALREADY_MEMBER` branch (`actions.ts:28-32`) — which the e2e itself exercises as the expected second
attempt (`e2e/admin-core-recovery.e2e.ts:76-80`). The retained values are a design decision, but they
are retained silently and the copy that follows ("this email is already registered here") describes
the *first* submission's outcome as an error.
**Prevent:** an interaction test asserting that after a successful invite the reopened form is either
cleared or explicitly marked as a repeat; today `AdminActionForm.test.tsx` covers error retention but
has no case for the post-success state, so the assertion is missing rather than failing.

**Pass rows worth keeping (agreement between layers, not defects):** the self-deactivation option and
the `SUPER_ADMIN` row are hidden exactly where the service refuses them (`page.tsx:205-206,272-274`
↔ `users.service.ts:181-185,334-348`); `displayName`/`email` are bounded identically in the client,
the domain and the server error copy; `scope` and `active` are written by both paths that render
them; the filter's active state survives the round trip in both controls (`page.tsx:148,152`).
