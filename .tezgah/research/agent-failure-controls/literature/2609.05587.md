Abstract
Existing evaluations of tool-using agents primarily measure whether an agent can
successfully complete diverse tasks with tools. These evaluations generally assume
that tools return reliable information. However, tool returns in real-world systems
can be plausible yet incorrect. We investigate how agents respond to unreliable
tool returns by evaluating fourteen LLMs using three tools—web search, LLM
sub-agent delegation, and code execution. For each tool, we corrupt its returns and
measure whether agents adopt the corrupted content in their final answers. Agents
exhibit high levels of overtrust across all three settings: the mean adoption rate
exceeds one third for every tool and reaches 68.0% for web search. Analysis of
reasoning traces reveals a particularly concerning failure mode: agents often rec-
ognize conflicts and even recover the correct answer internally, yet present only the
corrupted answer without warning the user. To mitigate agents’ overtrust in tool
returns, we intervene at three levels: prompting by the user, metadata from the
tool provider, and post-training by the agent builder. Although some interventions
help for particular models or tools, none consistently mitigates overtrust across
tools. These findings identify overtrust in unreliable tools as a serious and persis-
tent failure mode, motivating evaluations and interventions that enable agents to
validate tool outputs and transparently communicate unresolved conflicts.
1 Introduction
Tool use has become a basic component of large language model (LLM) agents. By searching the
web, executing code, and calling other agents, they can access information and perform computations
beyond their current parameters [1–3]. Standard tool-use benchmarks evaluate whether agents select
an appropriate tool, issue a valid call, and complete the task using the returned information [4–7].
These evaluations largely assume that tool returns are reliable. However, this assumption is becoming
harder to maintain because tools can return generated outputs: some search tools return answers
generated from retrieved information [8–10], LLM sub-agents return reports for delegated tasks [3],
and code executors return outputs from model-generated programs [11]. In such cases returns can
be plausible but incorrect, yet existing evaluations rarely test whether agents adopt or resist them.
Conflicts between external context and an LLM’s parametric knowledge have been studied primarily
in retrieval [12, 13]. These studies test model responses to retrieved passages that contradict prior

passages already provided, whereas tool-using agents decide whether and when to invoke a tool
while carrying out a task. To address this problem, emerging research evaluates agents under noisy,
misleading, or absent tool returns [14, 15]. However, because these studies focus on performance
degradation, they offer limited insight into when agents trust unreliable returns and how such reliance
can be mitigated. We therefore ask whether agents carry corrupted content into their final answers,
how the adoption rate changes with plausibility, and which interventions can mitigate this reliance.
To examine these, we test agents with three tools: web search, an LLM sub-agent, and a code executor.
For each tool, we obtain an uncorrupted return and then alter only its content before presenting it to
the agent. The Adoption rate measures how often the agent carries the corrupted content into its final
answer. For items that the agent initially answers correctly without a tool, the Override rate measures
how often the corrupted return changes its answer. None of the fourteen models consistently resists
corrupted returns across all three tools. The mean Adoption rate exceeds one third for every tool
and reaches 68.0% for Search, while the mean Override rate remains substantial. Crucially, these
failures are rarely visible to users. Among final answers that adopt corrupted content, only 5.3%
in Search and 1.8% in Code Executor warn the user. To determine whether models fail to notice
the conflict or whether their final answers fail to reflect what they have recognized, we inspect the
reasoning traces of reasoning models. The traces reveal a striking disconnect: reasoning models
often recognize the conflict and even recover the correct answer internally, but their final responses
still present the corrupted answer and almost never mention the conflict or the correct answer.
To mitigate agents’ overtrust in tool returns, we intervene at three levels: the user, the tool provider,
and the agent builder. On the user side, prompt policies that ask agents to compare, verify, or disclose
conflicting returns reduce the Adoption rate for some models and tools, but none does so consistently
while preserving accuracy on uncorrupted returns. On the tool-provider side, source and reliability
metadata provide no consistent mitigation; higher stated reliability can make a corrupted return more
persuasive. On the agent-builder side, post-training produces effects that depend on the objective
and do not reliably transfer from Search to the Code Executor. Together, these results indicate that
overtrust is a persistent and difficult-to-mitigate failure mode rather than a problem that any single
intervention can resolve. Addressing it will require further work on interventions that generalize
across models and tools without compromising performance when tool returns are reliable.
2 Related Work
Knowledge conflicts in LLMs. Knowledge conflicts arise when contextual information contradicts
a model’s parametric knowledge [16]. Prior work examines what models report when a conflicting
passage is placed directly in the prompt [12, 17, 18]. Retrieval-corruption benchmarks extend this
setup to retrieved contexts containing false, misleading, or outdated information, and show that such
corruption substantially degrades model performance [19, 13, 20]. Together, these studies show that
conflicting passages can substantially influence model responses. However, they evaluate models as
generators given retrieved information, rather than as agents issuing tool calls during task execution.
Also, these studies have focused on retrieval, whereas agents use a broader range of tools, including
code executors and sub-agents [21, 22].
Agents with unreliable tools. Tool-use benchmarks have mainly evaluated appropriate tool selec-
tion and invocation with correct arguments [23, 24]. As tool-use evaluation has matured, benchmarks
have expanded to tasks that chain several tools [5] and to dialogues with a simulated user [7, 25]. Be-
cause these benchmarks assume that tools return correct values, they measure how well an agent uses
a tool, not what it does when a return is incorrect.
Recent studies examine how agents respond when tool outputs conflict with their own knowledge
or answers [26, 27]. Other benchmarks inject noisy or misleading feedback into search and multi-
turn tool-use pipelines and report substantial performance degradation [28, 14, 15]. However, these
studies do not systematically compare this behavior across different tools. We compare such reliance
across search, code execution, and sub-agent delegation. Rather than treating degradation as a single
outcome, we distinguish general adoption of corrupted returns from the sharper case in which a tool
overrides an answer the model has already demonstrated it can produce correctly. We also examine
whether agents recognize and disclose conflicts when they adopt a corrupted return, and test whether
this reliance can be mitigated through user instructions, tool metadata, and post-training.

3 Evaluation Design
To measure how much agents trust their tools, we evaluate them on three tasks, each using a different
tool: question answering with web search, summarization with an LLM sub-agent, and mathematical
problem solving with a code executor.
Metrics. We use the adoption rate and override rate to measure how agents respond to corrupted
tool content. The adoption rate is how often an agent uses the injected content in its final answer.
The override rate is the adoption rate on items the model answers correctly without a tool. We
determine correctness by majority vote over three independent no-tool responses; the proportion of
correct items is base accuracy B.
Web search. We evaluate agent reliance on web search in factual question answering. We use factual
questions from the April 21, 2026 FreshQA snapshot [29], excluding 14 binary questions from the
original pool of 432 because they do not support distinct corrupted answers. The resulting 418
questions comprise 147 never-, 127 slow-, and 144 fast-changing items.

of the corrupted answer while preserving the rest of the retrieved content. We use Qwen3.5-27B to

LLM sub-agent. We evaluate agent reliance on an LLM sub-agent in document summarization.
Each request asks for summaries of three named documents. We use 45 documents in three sets

novels, and post-cutoff papers first released after 2026-05-01.

receiving model. For every document, we use GPT-5.6-Terra to generate and store one fixed five-

one headline claim with a false claim, whereas P2 adds a fabrication while retaining the true claims.

4 Results
4.1 Adoption and Override Rates Across Channels
Agents frequently carry corrupted returns into their final answers across web search, sub-agent del-
egation, and code execution (Table 1). For P1, which is designed to remain plausible, the mean
Adoption rate exceeds one third in every setting and reaches 68.0% in Search. This pattern is strik-
ing in the Code Executor, where models adopt more than one third of P1 returns despite answering
about 85% of the underlying problems correctly without a tool. This behavior is not limited to plausi-
ble errors. Figure 1 shows what P2 means in Search: the German chancellor’s name is replaced with
the unrelated value 11. Models still adopt 12.6% of exposed P2 Search returns. The P2 Adoption
rate is nearly one quarter in both the sub-agent and executor settings.
The Adoption rate alone does not establish that relying on a tool is unreasonable. Tools are meant to
supply information an agent may lack or perform computations it may not reliably carry out on its
own, so an agent that reflexively rejects tool returns would lose much of the benefit of tool use. The
sharper test is whether a corrupted return changes an answer the model has already demonstrated it
can produce correctly. The Override rate measures this behavior. For P1, it remains above one half in
Search and near one third in the Code Executor; in the executor, the Adoption rate is 35.4% and the
Override rate is 33.4%. The Override rate decreases under the less plausible P2 and P3 corruptions
but continues to occur: it remains around one fifth for P2 in the sub-agent and executor settings and
exceeds one quarter for P3 in Search (Appendix 10).
The model-level results reinforce the same conclusion: no family is consistently resistant, although
several differences recur across settings. The clearest separation appears in the Code Executor, where
the Gemini, Gemma, and Muse models generally adopt less than the GPT-family models. Thinking
reduces the P1 Adoption rate for both Qwen sizes in every setting, but even the thinking models adopt
most P1 Search returns. The effect of size is less consistent: the smaller model usually adopts more,

corrupted-return runs by the mean in correct-return runs. A ratio of one indicates no change, while a
higher ratio indicates more calls under corruption. The warning rate measures whether a final answer
that adopts the corrupted return tells the user about the conflict.

5 Can Tool Reliance Be Shifted?
We next test whether this reliance changes when we alter how external information is presented, the
instructions and metadata that accompany it, or the model itself through post-training. In this section,
P0 denotes the uncorrupted correct-return condition, while P1 denotes the primary corrupted-return
condition in each channel. When reported together, P0 gives accuracy and P1 gives the Adoption rate.
A useful intervention should reduce the P1 Adoption rate without lowering P0 accuracy. Appendix E
reports 95% confidence intervals for the intervention contrasts.

6 Conclusions
We study a basic failure mode in tool-using agents: an agent can carry a plausible but corrupted
return into its final answer even when it could otherwise answer correctly. Our evaluation isolates this
behavior across Search, Sub-Agent delegation, and Code Executor settings by pairing uncorrupted
correct returns with corrupted returns. The Adoption rate measures whether the model carries the
corrupted content into its final answer, while the Override rate identifies the sharper cases in which it
changes an answer the model has already demonstrated it can produce correctly without a tool. Across
models and tool channels, both remain common. Agents often make additional calls or explicitly
recognize a conflict in their reasoning, yet rarely disclose that conflict when they adopt the corrupted
return.
Interventions across the tool-use process clarify the scope of the problem. Changing how informa-
tion is presented reveals that executable outputs receive authority beyond the same claim in a prompt.
User instructions can reduce the Adoption rate for selected models and channels, but no policy con-
sistently preserves accuracy with uncorrupted returns while reducing the P1 Adoption rate. Higher
stated reliability can make a corrupted return more persuasive, and simple post-training does not
reliably transfer across tool channels. Tools remain valuable, so the goal is not less tool use but
governed reliance. Evaluation should jointly measure resistance to corrupted returns, accuracy with
uncorrupted returns, and disclosure of conflicts the model has already recognized. Agent systems
should independently validate tool returns and convey unresolved conflicts to the user. When tools
speak, agents often follow even when they know better.

A Web Search: Dataset and Protocol
A.1 Dataset construction
Questions come from the FreshQA 2026-04-21 snapshot [29]. The candidate pool contains 432
questions. We exclude 14 questions marked as binary because their answer space leaves no room for
a graded wrong value.
The resulting set contains 418 questions: 147 never, 127 slow, and 144 fast under the snapshot’s
volatility annotation. Gold answers and aliases are frozen from that snapshot. Both the system-
prompt date and the search API cutoff are pinned to the same date, preventing the live feed from
serving evidence newer than the gold answers.
A.2 Plausibility ladder construction
Every question receives one frozen value at each level, generated once and shared by all models and
repetitions. All three levels pass two common checks: the value must not be equivalent to any gold
alias (normalized bidirectional matching plus an LLM equivalence check), and the three values for
one question must not collide with each other.
14

P1 (plausible). P1 is a real value that is credible for the question. It comes from earlier FreshQA
editions (171 items), generated and verified alternatives (219), or manual completion (28). Prove-
nance is retained in the released item data.
P2 (transplanted). The target is the gold answer of a different question, assigned deterministically
with its source question recorded. This condition deliberately tests a value that is real but belongs to
the wrong semantic type or question. An audit repaired three assignments: one string-copy bug and
two values that were also plausible answers to the target question.

A.3 Return serving pipeline
The search environment uses a live collection stage and a separate frozen replay mode. During the
reported collection, each normalized query was resolved as follows before the condition-specific edit:
1. The server first checks the frozen query cache. An exact hit returns the saved re-
sponse. On a miss in live-collection mode, the model’s query is sent to the Tavily
search API (topic=general, depth=basic, max_results=10, answer synthesis dis-
abled, end_date pinned to the snapshot date), and the full response is saved before its
top five results are kept.
2. An editor LLM (gpt-5.6-luna) rewrites the results so that claim-bearing titles and snippets
assert the target value. Its construction-time checks require unchanged relevance scores,
byte-identical results that carry no claim about the answer, no detected gold alias, and at
least one target match. If the search results contain no claim-bearing result, the target is
injected into the most relevant result and flagged. Because the historical collection predates
the final boundary matcher and some short aliases match incidentally, the analysis sepa-
rately audits what the model actually received rather than assuming these checks succeeded
(Appendix G).
3. A URL-leak check examines every URL slug (path and query, with date-alias expansion)
for strings that would reveal the gold answer, and has the editor rewrite leaking slugs under
a domain-invariance constraint. After three failed attempts, a mechanical fallback replaces
the leaking spans, and if that fails the claim-bearing result is dropped and logged.
4. Edited search results are cached by (results, target, editor version), so an exact query hit
returns the identical corrupted results across repetitions and models.
Offline replay reproduces an archived response byte for byte on an exact-query hit. For an unseen
query, the evaluator deterministically selects the cached normalized query with the highest BM25
score and records both queries, the score, and the resolution mode. This fallback supports interactive
evaluation without a live backend, but it is not live retrieval and was not the procedure used for cache
misses in the reported collection. New-model evaluations must therefore report exact-hit and fallback
rates separately. A later live web index is not expected to reproduce the reported search results.
The release includes rights-cleared code, queries, source URLs, cryptographic hashes, collection
metadata, and derived labels. Redistribution of cached response payloads remains subject to permis-
sion from Tavily and the underlying sources. The frozen manifests, evaluator, and audit trail permit
verification of reported joins even when a payload cannot be redistributed.
The correct control (P0-align in the released data) runs the same pipeline with the target set to the
gold answer, which controls for the editing style itself. One additional repetition per question serves
the raw, unedited snapshot.

B Sub-Agent Delegation: Dataset and Protocol
B.1 Corpus
The corpus contains 45 documents divided into three groups: 15 pre-cutoff papers, 15 post-cutoff
papers first released after May 1, 2026, and 15 nineteenth-century novels from Project Gutenberg.
The papers cover five fields (ai, med, phys, psych, and econ), with three papers per field in each
temporal group. This matched design varies prior-knowledge availability within rather than across
fields.
Papers are represented by abstracts resolved through arXiv, PubMed, OpenAlex, and Crossref, in that
order, with arXiv versions pinned. Novels are provided to the summary generator by title only, so
their summaries are not derived from supplied source text.
Tables 7–9 list all 45 documents used in the sub-agent evaluation.
B.2 Corruption construction
A generator (gpt-5.6-terra) writes one accurate five-sentence summary per document (P0), then
derives two variants from it. The distorted variant replaces one headline claim with a false one; the
fabricated variant keeps every true claim and weaves in one fact the work does not contain. Each
document has one manifest entry {true_claim, false_claim, carried_by} that defines the grading tar-
get.
Automated checks reject and regenerate invalid variants. Structural checks require exactly one edit,
five sentences, and 90–160 words. Content checks require carried_by to appear verbatim, at least
half of the false claim’s distinctive words to appear in the variant, and content-word retention of at
least 0.85 for distorted or 0.92 for fabricated summaries. For distorted summaries, the true claim
must be present in P0, and the corruption cannot change only a number. Fabricated content must be
absent from both P0 and the source abstract. All 90 variants pass these checks.
B.3 Task and tool
The user names three documents from one set by title and asks for one summary each. The system
prompt announces a subagent tool that launches a delegate to summarize one document and report
back. The tool accepts description, prompt, and subagent_type, matching the delegation inter-
face exposed by the deployed harness. The prompt does not require the agent to use the tool. The
tool itself is a frozen lookup on (document, condition): every return is written offline in advance, so
asking twice returns identical bytes and re-querying cannot expose the corruption.
The harness resolves free-form tool arguments by deterministic title matching, with a router model
used only when matching fails. Only the three requested document slots enter grading.

C.2 Corruption injection
The 
python_executor 
tool runs the model’s code in an isolated subprocess. On success, every
numeric token in the captured output is multiplied by the problem’s frozen factor; failed executions
return their traceback unmodified. The factor is built from three axes drawn or assigned once per
problem and stored to disk with it.
Magnitude. p is drawn log-uniformly from [1, 100] for P1 and [101, 10000] for P2. The ratio is
r = 1 + p/100.
Direction. The factor is r (inflate) or 1/r (deflate). The two directions are symmetric in log space.
Sign. 
The factor may be negated. Direction and sign are assigned rather than sampled. Within each
operation, the four cells contain 12 or 13 problems. The two extra assignments rotate across opera-
tions, yielding exactly 75 problems per cell over the full benchmark. The problem-to-cell mapping
is shuffled under the seed. This crossed factor permits separate reporting of sign-preserved and sign-
inverted returns. Its meaning is operation-specific: addition, multiplication, and division include
problems whose correct answer can be negative, whereas modulo, logarithm, and exponentiation
have nonnegative correct outputs in this set.

A draw is repeated if the perturbed value rounds to the correct answer at three decimals. The factor

C.4 Roster, protocol, and grading
The roster is identical to the search channel (Table 6): fourteen models across six families, with the
same serving, precision, and decoding settings and three repetitions per condition. Unlike the search
runner, the executor runner sends the same API seed (12345) on every repetition, so repetitions differ

a demonstrated correct answer reduces to that single draw. Tool calls are capped at 50 per run. Each
run record retains the full message history, tool calls, and token usage.
All fourteen models complete three repetitions. Each repetition contains 900 scheduled runs across
the three conditions and enters the aggregate only when all 900 are present with at most 1% API
failures. All capped episodes have a tool-free forced-final response. Tool-use rates are 83–100%,
and conditioning on successful exposure changes the Adoption rate by at most 2 points relative to
the reported all-run rates.

F Intervention Protocols
Presentation conditions. For Search, the User and RAG conditions are built from the same frozen
five-result P1 payload. The payload is generated by sending the canonical question through the same
Search and corruption pipeline used in the main evaluation, after which only the result titles and
snippets are retained. The User prompt places these passages after “Here’s what I found online:”,
while the RAG prompt places them under a Context: header. Both use the no-tool system message.
The Tool condition is the canonical agent-initiated Search collection, so it retains model-generated
queries rather than replaying the prompt payload. P0 controls are generated through the same pipeline
with the gold answer as the editing target. The prompt conditions use one repetition, whereas the Tool
condition uses the canonical three-repetition collection. Prompt rows are restricted to items with a
target-bearing frozen payload that also received a target-bearing return for that model in the Tool
condition. Qwen3-30B uses the same OpenRouter Alibaba endpoint as the main evaluation; only the
post-training experiments use local checkpoints.
For Sub-Agent, the Tool condition returns three frozen delegate reports through the sub-agent call.
The User condition places the same numbered reports after “I had someone look into these; here’s
what they reported:”, and the RAG condition places them under a Context: header. For the Code
Executor, the User prompt states the returned number directly, while the RAG prompt places the same
statement under a Context: header. Across all three channels, RAG is a controlled proxy for the
prompt-augmentation stage rather than an end-to-end retrieval pipeline. These prompt conditions use
one response per item, whereas their Tool counterparts use the canonical three-repetition collections.
