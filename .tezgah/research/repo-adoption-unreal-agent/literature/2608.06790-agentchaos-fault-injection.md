## What it gives

The instrument question that comes attached to any execution engine. AgentChaos injects
faults at the one interface every agent system shares when it calls a model — the HTTP
request-response boundary — non-intrusively and at runtime, with a fault taxonomy adapted
from classical distributed-systems classifications (crash, omission, value) and aimed at
specific response fields such as `message.content` and `tool_calls`, so it can produce
the faults that matter to a tool loop: truncated responses and corrupted content.

It positions itself against three prior classes by their limits, and each limit is an
argument for a runtime: offline methods perturb completed traces and so never trigger real
runtime behaviour such as **retries or early termination**; agent-oriented runtime methods
inject semantic failures by rewriting prompts or outputs and must be reimplemented per
target system; traditional HTTP/OS-layer injection treats the response as an opaque byte
stream and cannot modify named fields.

## What it means for tezgah

The retry and early-termination behaviours this instrument exists to observe are
behaviours of **a loop that owns the call sequence**, so the test harness presupposes the
engine. tezgah's hooks do not own the call sequence — the host does. This is a second,
independent reason the async engine does not fit, and it is the reason to state plainly
what tezgah's fault testing cannot reach rather than to build a runner for it.

The surveyed repository's own answer to the same problem is in-tree and non-transferable:
`harness/coordinator/fault_fakes_test.go` and `fault_fuzz_test.go`, a process that can be
faked because the harness owns the loop — the technique this line's report recommends
tezgah borrow as a *rule* (`docs/testing.md`), not as a harness.
