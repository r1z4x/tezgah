# Do Coding Agents Deceive Us? Detecting and Preventing Cheating via Capped Evaluation with Randomized Tests

- id: 2606.07379
- class: formal
- source: alphaxiv (report), confirmed by the keyword channel against openalex
- date: 2026-06-05
- reading: report read; the mechanics section in full, the results section skimmed
- why read: the layer's question is how a harness refuses a claim the session cannot
  back; this paper is the closest published mechanic - make the achievable score
  lower than perfect so a score above it is *statistical evidence* rather than a
  judgement call.

## What it claims
- A benchmark can be built so that the best non-cheating policy scores at most
  `B = 1/M`, by admitting `M` equally valid outputs and accepting only one, sampled
  uniformly. Performance above `B` is then a **cap violation**, testable with a
  one-sided binomial test.
- Two shapes: task-level (one cap value per task) and case-level (a cap value per
  test case; the program must return `(original_result, code)`).
- `CapReward` turns the same cap into a training signal that is strictly increasing
  up to `B` and strictly decreasing beyond it, so no policy that exceeds the cap can
  maximize it.

## Quotes (verbatim, from the alphaxiv report text fetched through orx)
- "Performance significantly exceeding `B` then serves as a statistical indicator
  of cheating."
- "a score substantially exceeding it statistically interpretable as evidence of
  cheating"
- "The function thus penalizes performance that significantly deviates from the cap
  `B`, both above and below."

## What transfers to a hook-based harness
- The **expected value must be built in by the producer**. The cap works because the
  harness knows the value a non-cheating run can produce. A reader cannot recover it
  afterwards, which is E1's finding from the other direction.
- A cap violation is decidable arithmetic, not a semantic judgement - the property
  the gate needs if it is ever to refuse a claim rather than warn about it.

## What does not transfer
- Their setting is an evaluation with hidden tests; a session answering a user has
  no hidden test set, so "the cap" has to be manufactured (a fixture whose expected
  value the harness itself wrote), which is a design change, not a rule.
- The binomial machinery is for a population of tasks; a single session's claim has
  no population to test against.
