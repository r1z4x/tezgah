## The question: what happens when the create-user form is submitted with its fields left empty?

**Answer.** Nothing stops it in the browser: the Create User modal has no `required`, no per-field error
channel, no `disabled` guard, and is not a `<form>`, so an empty submission goes straight out as
`{"email":"","password":"","full_name":"","role":"viewer","tenant_id":""}`; the server rejects it with
`400 {"success":false,"error":"email, password, and tenant_id are required"}`, which the client surfaces
only as a toast. The user is told three field names in one English sentence, no field is marked, no
message lands beside a field, and the modal stays open with the typed values intact.

End-to-end trace, each hop cited:

| Hop | What happens | Citation |
|---|---|---|
| Form state | initialised empty; `role` is **not** empty — it defaults to `'viewer'`, so the payload always carries a valid role | `admin/frontend/src/pages/Users.tsx:36` |
| Form's own guards | `FormInput` accepts `required` and `error`, but the create modal passes **neither** for any of the four fields | `components/ui/FormElements.tsx:4-27` vs `pages/Users.tsx:248-250` |
| Submit control | plain `<button onClick={() => createMut.mutate()}>`, `disabled` only while a request is in flight; no `<form>` element, so no native validation and no `novalidate` question arises | `pages/Users.tsx:263-266` |
| Who renders the label | `label="Email"`, `label="Password"`, `label="Full Name"` with no ` *` marker (`required` not passed) | `pages/Users.tsx:248-250`; `FormElements.tsx:11` |
| Tenant field | `TenantSearchSelect`, empty by default; its placeholder is the only thing reading "Search tenant" | `pages/Users.tsx:256`; `components/ui/TenantSearchSelect.tsx:20` (default text), `:113` (rendered) |
| What the client sends | `createUser(form)` posts the object verbatim — no trimming, no omission of empty fields | `pages/Users.tsx:49-53`; `api/admin.ts:384-387` |
| Handler body type | untyped `Json<serde_json::Value>`; each field read with `.unwrap_or("")` | `admin/backend/src/handlers/admin.rs:892-905` |
| Handler's own check | `if email.is_empty() \|\| password.is_empty() \|\| tenant_id.is_empty()` → **400**, message `"email, password, and tenant_id are required"` | `handlers/admin.rs:906-912` |
| Error body shape | `{"success": false, "error": <msg>}` | `handlers/admin.rs:36-41` (`fn err`) |
| Where the client puts it | `toast.error(e?.response?.data?.error ?? 'Failed to create user')` — no `error` prop is ever bound to a field | `pages/Users.tsx:52`; `api/admin.ts:60-125` (401-only interceptor; 400 rejects straight through) |
| What survives | modal stays open; `form` is untouched; the success branch that resets it never runs | `pages/Users.tsx:51` (reset only in `onSuccess`) vs `:245`, `:259` (close paths) |

Boundary facts of this answer, so it is not read as a measurement:
- A **partially** filled submission diverges: with a 1-character password and a tenant chosen, the message
  becomes `"Password must be at least 8 characters"` (`handlers/admin.rs:914-921`); with a role of
  `super_admin` and everything else filled, `"Invalid platform role"` (`handlers/admin.rs:879-880`).
- Requiredness is enforced **server-side only**; the only client-side gate anywhere in this flow is
  `TenantSearchSelect` handing back a string, and the sibling create flows in this same SPA do it
  differently (finding F2).
- Not checked: whether a browser's own autofill or a password-manager extension alters the payload; the
  answer above is the payload the component builds (`pages/Users.tsx:49-53`).

## Findings, most severe first

Severity is the skill's 0–4 scale (frequency x impact x persistence). Every finding names its evidence
class; all are `code`.

**F1 — The create modal and the role editor offer `super_admin`, an option the service always refuses.**
severity 3. `Users.tsx:11` (`ALL_ROLES` includes `super_admin`) and `:85` advertise it; `admin.rs:873`
(`ADMIN_ASSIGNABLE_ROLES = ["admin","operator","viewer","api_user"]`) and `:879-880` reject it with
`400 "Invalid platform role"`. `admin.rs:8899` even asserts `!ADMIN_ASSIGNABLE_ROLES.contains("super_admin")`.
The detail panel's role buttons take the same list (`Users.tsx:179`), so a super_admin clicking "super
admin" gets the same refusal. An offer the system forbids, on two surfaces, for the one account type most
likely to try it (frequency: high, impact: the offer is dead, persistence: until someone reads both files).
*Prevent:* derive both surfaces' option list from a single source the server also enforces (a
`/admin/meta/roles` response or a shared constant), plus an e2e assertion that every role option the create
modal renders produces a 2xx.

**F2 — The create form has no client-side guard at all, while the same SPA's other create flows do.**
severity 3. `Users.tsx:248-250` pass neither `required` nor `error` to `FormInput`, and `:263` disables the
button only on `isPending` — the empty submission reaches the network (the question above). Sibling
convention, both sides cited: `Tenants.tsx:164` marks `required` and `:184` disables on `!form.name`;
`ApiKeys.tsx:229,270` does both; `Requests.tsx:57,318` gates the wizard's final step on `password.length >= 8`.
Three sibling flows validate; this one is a form in appearance only. *Prevent:* one shared
`useRequiredFields` guard plus an e2e step that clicks Create with empty fields and asserts zero network
requests — the assertion the sibling pages would already pass.

**F3 — The server's single-string error is delivered as a toast, bound to no field.**
severity 3. `admin.rs:907-911` returns `"email, password, and tenant_id are required"`; `Users.tsx:52`
puts it in `toast.error`; no `FormInput` in this modal receives `error` (`:248-250`), so no field is
marked and no message sits beside one. SC 3.3.1/3.3.3 items, which axe-core has no rule for. The 400 body
shape is `{"success":false,"error":…}` (`admin.rs:36-41`) and the client reads exactly that key
(`Users.tsx:52`), so the wiring to fix this already exists and is unused. *Prevent:* an e2e assertion that
after an empty submit each empty field's `aria-describedby` target is non-empty and the modal's error
summary receives focus.

**F4 — Closing the create modal keeps the abandoned values; only success resets them.**
severity 2. Cancel (`Users.tsx:259`), the header's close (`:245`) and the overlay click (`Modal.tsx:18`)
all just set `showCreate=false`; the reset lives only in `onSuccess` (`Users.tsx:51`). Reopening shows a
previous attempt's email and name with an empty password, which reads as a partially saved record.
*Prevent:* reset in the modal's `onClose` handler (one place), asserted by a component test that types a
value, closes, reopens, and expects empty fields.

**F5 — The list is unpaginated and the counts silently redefine themselves.**
severity 3. The client pins `limit: 200` (`Users.tsx:46`) and never passes `offset`; the server supports
both and returns `total` (`admin.rs:4396-4408`, `:4458`). The header says `${allUsers.length} users across
all tenants` (`Users.tsx:95`) and the four stat cards count the same slice (`:101-104`) — so with more than
200 users the page reports a number that is not the population, and after a search the same words mean
"matched". `components/ui/Pager.tsx` exists and `ThreatIntel.tsx` is its only consumer — a convention
deviation with both sides cited. *Prevent:* render `total` next to the fetched count and mount `Pager`;
assert the header string equals the API's `total` in an e2e run with >200 fixture rows.

**F6 — A detail endpoint and its client function have no caller: the panel never re-reads a user.**
severity 2. `admin_get_user` (`admin.rs:4469`, route `main.rs:283-286`) and `fetchUser` (`api/admin.ts:379-382`)
form a dead pair. Absence proof: `grep -rnw "fetchUser" admin/frontend/src --include=*.ts --include=*.tsx`
(run from the repo root) returns exactly one line — the definition at `api/admin.ts:379`; no page or
component imports it (`fetchUsers`, plural, is called at `Users.tsx:46` and `UserSearchSelect.tsx:29`).
The panel renders from the list row (`Users.tsx:133-196`), so anything changed outside this
tab — a login, a role change by another admin — is invisible until a full list refetch.
*Prevent:* call `fetchUser(selectedUser.user_id)` on panel open (the function and the route already
exist), with one e2e assertion that mutating a user out of band changes the open panel.

**F7 — `last_login_at` is carried by the contract and rendered by no surface.**
severity 1. Returned by the list query (`db.rs:485`) and the list handler (`admin.rs:4449-4458`), typed in
the SPA (`types/admin.ts:94`), and read by nothing in `Users.tsx` (`created_at` is the only timestamp the
detail panel shows, `:164-172`). *Layering note:* this column is the only evidence a deactivation or an
unused account produces, so the omission costs the operator the one fact that would justify acting.
*Prevent:* render it in the detail panel next to Created with an explicit "Never signed in" for null;
assert the rendered row in an e2e check.

**F8 — The modal has no dialog semantics and no focus management.**
severity 3. `Modal.tsx:14-25`: no `role="dialog"`, no `aria-modal`, no `aria-labelledby`, no `aria-label`,
no `Escape` handling, no focus move on open, no focus return on close; the backdrop's `onClick` closes it,
so a stray click discards the form (compounding F4). The visible title is an `<h2>` with no `id`
(`Modal.tsx:48`), so it cannot even be referenced. This component is shared, so the defect is product-wide,
not Users-specific. *Prevent:* fix `Modal` once (role, labelled name, focus trap, Escape, restore focus);
assert with a component test that `Escape` closes and that focus is on the first input after open. axe-core
partially covers this, and SC 2.4.7 focus visibility is a hand-check that cannot be done from source.

**F9 — The users table has no accessible name, no `scope`, and no sorting.**
severity 2. `DataTable.tsx:28-42` renders `<table>` + `<th>` with neither `scope` nor a caption, and there
is no `aria-label`; `Users.tsx:110` passes only labels. Sorting does not exist anywhere in the feature even
though the table is the operator's main surface and the server returns `created_at DESC` (`db.rs:492`) —
so "the newest user" is a position, not a control. *Prevent:* add `scope="col"` plus an `aria-label` in
`DataTable`, and a sortable-header test for one column; axe-core catches the header half, nothing catches
the absent-sorting half, so that stays a review item.

**F10 — Deactivate is irreversible from the UI, unconfirmed, and unnamed.**
severity 3. `Users.tsx:207-216` fires `toggleMut` on click; the object at stake is only in the panel title
(`:134`), the toast says `Status updated` (`:76`), and there is no undo — activation is the manual inverse
(`:215`), with no indication that it is available. SC 3.3.4 asks for reversible, checked or confirmed;
none of the three holds. `Deactivate` is styled as an equal-weight sibling of `Edit Profile`, so the
destructive choice is a coin flip in a two-button row. *Prevent:* name the user in a confirmation
("Deactivate ada@…? They can be reactivated."), or invert the affordance so deactivate is the secondary;
assert with an e2e step that a single click does not change `is_active`.

**F11 — The created user receives nothing.**

**F12 — Two routes create a user, with different typing and different activation semantics.**
severity 2. `admin_create_user` takes untyped `Json<serde_json::Value>` (`admin.rs:892-905`) and inserts

insert path, or an explicit note that activation differs by design; a contract test on the request body of

**F13 — A single click changes a user's role, with no confirmation and no undo.**
severity 2. `Users.tsx:179-195`: each role is a button whose `onClick` (`:184`) mutates immediately; `disabled` only

only, or an "Apply" step; e2e assertion that the role is unchanged until confirmation.

**F14 — The tenant picker is not a combobox to assistive technology, and cannot be opened by keyboard.**
severity 3 (shared component, used by every tenant-selecting form). `TenantSearchSelect.tsx:79-97`: the

required for every create (the question above) — is therefore mouse-only. *Prevent:* one combobox
primitive in `components/ui`, with a keyboard test (Down opens, Escape closes and restores focus, Enter
selects). axe-core cannot decide this; it is a hand-check against the APG pattern.
