## 1. The question, answered

> **What does this feature do when the create-user form is submitted with its fields left empty?**

### Answer

The form has **no guard of any kind**, so the submit is not stopped: the button is disabled only while a previous call is pending (`Users.tsx:263`), `createMut.mutate()` fires, and the client POSTs the empty values verbatim. The server rejects it with **HTTP 400 and the body `{"success":false,"error":"email, password, and tenant_id are required"}`** before any hashing or insert happens; the panel shows that string **only as a transient toast**, marks no field, moves no focus, and keeps the modal open with everything the operator typed still in place.

### Trace, layer by layer

1. **The form's own guards — none.**
   - The five controls are `FormInput`/`FormSelect`/`TenantSearchSelect` given only `label`/`value`/`onChange`/`type`: `Users.tsx:248-256`. The primitives *can* render requiredness and a field error (`FormElements.tsx:6-25` — `required`, `error`); the page passes neither.
   - Proof of absence, `grep -c "required\|novalidate\|<form\|error=" admin/frontend/src/pages/Users.tsx` → **0**.
   - There is no `<form>` element in the modal (`Users.tsx:244-271`), so there is no native constraint validation and **Enter does not submit**; the only submit path is the button's `onClick` (`Users.tsx:263`).
   - The modal adds nothing: `Modal` (`components/ui/Modal.tsx:16-31`) has no dialog role, no `aria-modal`, no Escape handling and no initial focus; it closes on backdrop click (`Modal.tsx:19`) and discards whatever was typed, with no confirmation.
2. **What the client sends.** `createUser(form)` → `api.post('/api/v1/admin/users', data)` (`api/admin.ts:384-387`) with `form = {email:'', password:'', full_name:'', role:'viewer', tenant_id:''}` (`Users.tsx:36`). CSRF is handled before it leaves: `client.ts:34-40` sets `X-CSRF-Token` from the `aibim_csrf_token` cookie on POST, which `middleware.rs:141-143` validates.
3. **What the handler does with a missing value.** `admin_create_user` reads each field with `and_then(as_str).unwrap_or("")` (`admin.rs:897-906`), so absent and empty are indistinguishable, then
   ```
   admin.rs:907-913
   if email.is_empty() || password.is_empty() || tenant_id.is_empty() {
       return err(StatusCode::BAD_REQUEST,
                  "email, password, and tenant_id are required");
   }
   ```
   That check runs **before** the role grant (`admin.rs:922`), before the min-8 check (`admin.rs:915-920`) and before the Argon2id hash (`admin.rs:928`), so an empty submit costs one cheap request and never reaches Postgres or the hasher. `full_name` is required by no layer (handler `admin.rs:899`; schema default `001_core_tenants.sql:74`; the form does not asterisk it).
4. **Where the error lands.** The response comes from `err()` → `{"success": false, "error": msg}` (`admin.rs:36-41`), and the page reads exactly that path: `toast.error(e?.response?.data?.error ?? 'Failed to create user')` (`Users.tsx:52`). `createMut`'s `onSuccess` resets the form (`Users.tsx:51`), `onError` does not — **the typed values survive a rejection** (a pass row).
5. **The three fields the toast names stay unmarked.** No `aria-describedby`, no error summary, no focus move: the toast is the entire error channel (`Users.tsx:52`), so SC 3.3.1/3.3.3 and the error-summary rule fail even though the server's message is specific and correct.

### The same question on the other create path (contrast)

`POST /api/v1/admin/requests/{id}/approve` fails *lexically the same way* with a different guard order: emptiness (`admin.rs:1100-1107`) → min-8 (`admin.rs:1107`) → role grant (`admin.rs:1114`) → hash (`admin.rs:1142`) → inline INSERT (`admin.rs:1152`). Same two messages, duplicated instead of shared (F14).

### What this answer rests on

`code` evidence only (source reading). The behaviour was **not** exercised: the admin backend (8081) and the admin SPA (5173) were both closed at read time (`curl -m 2` → `000` each) and the brief forbids builds and containers, so this artifact contains no `ui-observed` and no `behaviour` row. ## 7. Findings, by severity

Each carries one evidence class, a `path:line`, and a Prevent line. Every finding here is `code` evidence (source reading): with no runtime, no `ui-observed`, `behaviour` or `user-verbatim` row exists in this artifact, and that is itself the first limitation recorded in §9.

**F0 — severity 3 — first, the feature's own operation is not observable.**
"Did the operator get what they asked for" cannot be answered from the system's own data, so every triage decision in §10 rests on a count nobody can currently take.
- Audit rows are written **only on success**: `audit_admin_action` sits inside the `Ok(r) if r.rows_affected() > 0` arms (`admin.rs:806-818` role, `:850-865` deactivate, `:1006-1018` activate, `:4526-4537` update, `:8452-8463` permissions) and has no failure counterpart — so the count of *refused* role or permission attempts, which is exactly F2's and F3's exposure, exists nowhere.
- Nothing records the credential hand-off: the create response says "Activate after approval" (`admin.rs:967`) and writes no field saying the hand-off happened (`db.rs:521-523`).
- The audit writer is fire-and-forget by design: on a DB failure it warns and returns `Ok(())` so the caller still answers success (`admin.rs:44-60`, `:227-289`) — an audit gap is invisible to the operator who caused it.

*Prevent:* write a paired failure row (or a counter) for every refused mutation, and one `invited_at`/`delivered_at` state that the create path sets. Until then the two most useful ratios in §10 are unmeasurable, not merely unmeasured.

**F1 — severity 4 — the module-permission editor always opens empty and then saves what it shows, silently destroying stored permissions.**
`TenantDetail.tsx:337` reads the tenant-users list; its mapper returns five fields only (`api/admin.ts:364-369`, handler `admin.rs:776-779`); the Manage disclosure recomputes from the never-populated field (`TenantDetail.tsx:393`); Save writes `editModules` wholesale (`api/admin.ts:922-925` → `admin.rs:8438-8440` → `db.rs:957-958`, `UPDATE users SET permissions = $2::jsonb`). The only read path that could fill it, `GET /users/{id}/permissions` (`main.rs:337-341`, `admin.rs:8477-8494`), is called by nothing (absence proof: `grep -rn "permissions" admin/frontend/src` → the PUT plus reads of the undefined field). `AdminUser.permissions` is documented as populated (`types/admin.ts:96-97`) — intent and code disagree, both cited.
*Prevent:* wire the read path and pin it with an e2e that sets modules, reloads the tab and asserts they persist. No existing check can fail on this: it is the one finding most likely to recur unnoticed.

**F2 — severity 3 — the panel offers `super_admin` as assignable; the service refuses it.**
UI: `Users.tsx:11` (`ALL_ROLES`), `:85`, `:177-199`, `:252-253`; `TenantDetail.tsx:354`. Service: `admin.rs:873` (`ADMIN_ASSIGNABLE_ROLES`, four values, no `super_admin`) + `:879-881` → 400 "Invalid platform role". Documented intent on the same side: `admin.rs:871-872` ("super_admin can only be created via the CLI tool"), backed by `bin/create_admin/main.rs:1-5`.
*Prevent:* one shared source for the option list, plus a contract test asserting every option the UI offers is accepted by `validate_platform_role_grant`.

**F3 — severity 3 — an `admin` can demote or deactivate a `super_admin`, or themselves, and the sibling path proves a guard is expressible.**
`admin_user_role` checks only the *requested* role (`admin.rs:875-889`) and never the target's, while `db.rs:512-513` updates any row; `admin_user_deactivate` has no policy beyond being logged in (`admin.rs:835-865`, `db.rs:515-516`); middleware admits both roles only (`middleware.rs:36`, `:77`). The guard the SCIM path does implement — refusing to reactivate a platform admin from a lesser role (`admin.rs:5658-5663`) — shows the check is expressible here too. Impact: one unconfirmed click (`Users.tsx:207-216`) can lock the platform out of provisioning until the CLI bootstrap is run.
*Prevent:* extend `validate_platform_role_grant` to take the target's current role, with unit tests for (admin → super_admin), (admin → self) and (admin → peer); the module already unit-tests this function's style (`admin_dto.rs:408-413`).

**F4 — severity 3 — the list silently truncates at 200 rows, `total` is fetched and dropped, and the page states a population fact from the sample.**
`Users.tsx:44-47` asks for `limit: 200` and destructures only `data`/`isLoading`; `fetchUsers` returns `total` (`api/admin.ts:374-377`) and the server computes it (`admin.rs:4434-4444`, `:4458`, `COUNT_FILTERED` `db.rs:494-501`). Absence proof: `grep -c "offset\|Pager\|total" Users.tsx` → **0**. The header then reads "`{allUsers.length} users across all tenants`" (`Users.tsx:95`) and the cards count the page (`:101-104`). Sibling convention, i.e. the standard: `ThreatIntel.tsx:247` renders `Pager` with `total`, `Agents.tsx:86` sends a real `offset`, and `Pager.tsx:10-12` hides itself for a single page.
*Prevent:* an e2e on a fixture of 201 users asserting the header shows the server `total` and a pager exists.

**F5 — severity 3 — a failed load renders as "No users found" instead of an error.**
`Users.tsx:44` has no `isError`; `grep -n "isError\|QueryErrorState\|refetch" Users.tsx` → no hits, while 14 of the 16 pages use the component that exists for exactly this (`ApiKeys.tsx:31`, `Billing.tsx:21`, `components/ui/QueryErrorState.tsx`). Reachable by an `enterprise_admin` — accepted at login (`middleware.rs:61-63` inside `is_canonical_admin_panel_role`) and shown the Users nav item (`AdminLayout.tsx:31-38`, ungated) — whose every users call is then refused by `require_admin_access` (`main.rs:440-443`); also by an expired token.
*Prevent:* use the shared `QueryErrorState` here, plus one e2e asserting a 403 renders an error and not the empty text.

**F6 — severity 3 — no client-side guard and no field-level error path: an empty submit is a bare 400 toast.**
`Users.tsx:248-256` (no `required`, no `error`), absence proof `grep -c "required\|novalidate\|<form\|error="` → **0**; the submit button is live whenever not pending (`:263`); `FormElements.tsx:6-25` already supports both props; the server is authoritative (`admin.rs:907-913`); the surface's whole error channel is `Users.tsx:52`.
*Prevent:* an e2e that submits the empty modal and asserts three field-level messages, a summary, and focus moved — the SC 3.3.1 pair.

**F7 — severity 2 — password length is measured in bytes while the message speaks of characters.**
`admin.rs:915-920`, duplicated at `:1107` and `:8772`; `admin_dto.rs:136` shows the module's other convention (validator `length`, characters). "şifş" — 4 characters, 8 bytes — passes a check whose message promises 8 characters.
*Prevent:* a table-driven unit test with a 4-character multi-byte password asserting 400.

**F8 — severity 2 — two validation conventions in one handler module; create and update take raw JSON, and DB-width errors surface as 500s.**
`admin.rs:892-895` (`Json<serde_json::Value>`) with manual reads at `:897-906`, against the typed, `deny_unknown_fields`, length-validated DTO at `admin_dto.rs:134-138`; `admin_update_user` is untyped too (`admin.rs:4505-4512`) and turns a unique violation into 500 (`:4536-4542`) where create maps it to 409 (`:975-979`); the DB caps both strings (`001_core_tenants.sql:72,74`), so an over-long email from an API client is a 500 rather than a 400.
*Prevent:* a `CreateUserReq`/`UpdateUserReq` DTO pair of the same shape as the one already in the file — a type-level check, not a review item.

**F9 — severity 2 — a missing `role` silently becomes `viewer`, the same footgun already ruled out on the update path.**
`admin.rs:900-905` versus the documented intent at `admin_dto.rs:129-133` ("prior handler silently defaulted to `'viewer'` on missing field, which is a footgun"); the schema default agrees (`001:75`). An API call that omits `role` provisions a viewer and reports success.
*Prevent:* make `role` required in F8's DTO with a missing-field unit test.

**F10 — severity 2 — `tenant_id` is never checked to exist: a bad id is a 500, and a concurrent tenant delete hard-deletes the new user.**
`admin.rs:907-913` checks emptiness only; `db.rs:521-523` casts to `uuid`; the FK is `ON DELETE CASCADE` (`001:76`); the error map is a generic 500 (`admin.rs:981-984`). Only the UI's picker shields this (`TenantSearchSelect.tsx:62-72`); the API-client pass reaches it directly.
*Prevent:* a pre-insert existence check returning 400, with a test using a well-formed unknown uuid asserting 400 rather than 500.

**F11 — severity 3 — the end of the create action: nothing reaches the user, and the waiting queue is invisible.**
Create writes inactive and replies "Activate after approval" (`admin.rs:937`, `:967`); no mail or invite layer exists in the admin backend (grep in §2); activation is a separate click (`Users.tsx:207-216`); and no surface can filter to inactive users — the server's search covers email/full_name/role/user_id/tenant name (`db.rs:486-491`) and the panel's only filter is free text (`Users.tsx:107`). *Prevent:* a status filter plus a delivery step; nothing mechanical can assert "the user was told" until the artifact in §8 exists.

**F12 — severity 3 — no accessibility layer exists in the design system, so this surface is mouse-only and unannounced.**
`grep -rn "aria-\|role=" components/ui/` → **0** across 16 files; rows clickable with no key handling (`Users.tsx:114-120`); a modal with no dialog semantics, no focus management, no Escape (`Modal.tsx:16-31`); a picker that cannot be opened from the keyboard (`TenantSearchSelect.tsx:84-92`); table headers without `scope` or caption (`DataTable.tsx:26-40`); a search input without a label (`AdminPrimitives.tsx:60-76`). Violated: SC 1.3.1, 2.1.1, 4.1.2, 4.1.3, APG dialog and combobox. axe-core sees none of the SC 2.1.1 or 4.1.3 parts; those are hand-check rows, `[NOT CHECKED: no runtime]`.
*Prevent:* an axe sweep in the panel's CI catches the role/name/header subset; the keyboard and announcement halves need the running-app pass (`analyze-app`), not a lint.

**F13 — severity 2 — contract fields with no view, and one view field with no layer.**
`last_login_at` is returned (`db.rs:484`, `admin.rs:4454`) and typed (`types/admin.ts:94`, `api/admin.ts:37`) but rendered nowhere (absence proof in §3); `created_at` and `last_login_at` are selected by `LIST_BY_TENANT` (`db.rs:469-472`) and dropped by the handler's five-field JSON (`admin.rs:776-779`) although `AdminUser` declares them (`types/admin.ts:93-94`); `updated_at` has no reader at all.

**F14 — severity 2 — three creation routes for one action, divergent activation semantics, and two inline copies of a statement that already exists as a const.**
`POST /users` → inactive, via `db::users::CREATE_INACTIVE` (`admin.rs:937`, `db.rs:521-523`); `POST /requests/{id}/approve` → active, via an inline INSERT (`admin.rs:1152-1160`); SCIM upsert → active with a random password, via an inline INSERT (`admin.rs:5680-5696`). The approve path also takes its tenant solely from the reviewer's body (`admin.rs:1095-1100`) while no record holds the tenant the applicant asked for — `registration_requests` has no tenant column (`017_registration_requests.sql:6-20`) — so the decision cannot be checked against the application.

**F15 — severity 1 — the role and module vocabularies have four and two sources respectively, and the badge shows the drift.**

## 8. Capability-change proposal (required — the fix names a layer that does not exist)

Only F11's fix needs a layer the codebase lacks. Everything else is repairable inside layers that already exist — the `Pager` component, the `QueryErrorState` component, a typed DTO beside the existing one, a `db::users` statement that is already written — so those stay findings, not proposals.

**Capability.** A user created by an admin must be able to obtain a first credential without the creating admin carrying it out of band, and the system must record that the hand-off was offered.
*Falsified by:* a cited path that already delivers credentials. None exists (grep in §2; the SCIM path generates a password at `admin.rs:5680` and delivers nothing).

**Absence proof.** `admin/backend/src` contains no SMTP, mailer or invite symbol at all (grep above). `admin.rs:937` writes the row; `admin.rs:967` returns a message telling a human to finish the job; `db.rs:521-523` has nowhere to record an invitation state. Failing input: `POST /api/v1/admin/users` with valid fields → 201, an inactive row, and no artefact the recipient can use.

**Contract delta.** A `user_invitations` table — `id`, `user_id UUID UNIQUE NOT NULL REFERENCES users(user_id) ON DELETE CASCADE`, `token_hash`, `expires_at`, `consumed_at`, `created_by UUID REFERENCES users(user_id)`, `created_at` — plus `users.invited_at TIMESTAMPTZ`, as one migration; and the route delta `POST /api/v1/admin/users/{user_id}/invitation` → 201, or 409 when an unconsumed invitation exists. Rejectable artifact: the migration itself plus a schema-diff step in CI (`sqlx migrate run` then a `pg_dump --schema-only` comparison), which fails on any drift.

**Migration.** Expand: add the table and the nullable column, ship readers/writers that nothing yet calls. Migrate: backfill `invited_at` as NULL for every existing row — **tokens are deliberately not backfilled**, since an unredeemed token for a pre-existing user is a credential path into an account nobody asked to open. Contract: nothing is dropped; the dated step is retiring `is_active = false` as the approval convention, no earlier than **2026-11-01** (two minor releases after expand), named in the ADR rather than here.

**Rollout.** Flag `admin_user_invitation`, boolean, expected lifetime one quarter; initial exposure the platform `super_admin` cohort only; owner the admin-panel maintainer; abort threshold, >5% of invitation requests failing over a 24 h window → flag off and revert to out-of-band credentials. The kill switch is the flag, not a deploy.

**Verification.** The check that must fail before and pass after: with the flag on, `POST /users` writes exactly one `user_invitations` row and a non-null `users.invited_at`; with the flag off, it writes neither. Any check that also passes on the pre-change commit — "the user row exists", say — is rejected.

**Reversibility.** The new path writes one invitation row and one column. Restore: `DELETE FROM user_invitations WHERE user_id = $1; UPDATE users SET invited_at = NULL WHERE user_id = $1`. After a token has been redeemed, the deletion is one-way, so it is logged as an event rather than undone.

**Decision.** ADR "Credential delivery for admin-provisioned users". Context: create and SCIM both produce accounts whose users are never given a credential (`admin.rs:937`, `admin.rs:5680-5696`). Decision: an invitation token with an expiry and a `consumed_at`, delivered over the product's mail path. Status: proposed. Consequences: the app backend grows a redemption endpoint; the admin surface gains one row state and one delivery state; supersedes nothing.

**Appetite.** One week for expand plus writers behind the flag. Out of bounds: password reset, SSO, and any change to the login verifier. If the box ends with the flag dark, this finding stays open and out-of-band credentials remain the documented behaviour.

## 10. Axes this audit feeds

### Value (HEART: goal → signal → metric)

Goal: an operator can provision and maintain platform users and can see that each change took effect. Signals: provisioning ends with a user who can log in; the stored permission set is the one the operator set; a refused action is visible. Metrics, each with its definition and window — **none of the three is computable today**, and that is F0, not a footnote:
- *activated-within-7-days*: created users reaching `is_active = true` within 7 days of `created_at` (window: rolling 7 days). Computable: `users.created_at`, `users.is_active`. Blocked on F0's missing hand-off state if the question is "was the user told" rather than "was the row flipped".
- *permission-save fidelity*: permission saves whose stored `modules` array differs from the submitted one (window: per release). Computable from `users.permissions` after F1's fix; today the expected value is 100% loss, which is why F1 is severity 4.
- *refused-offer rate*: refused role/permission mutations over attempted ones (window: 7 days). **Not computable** — audit rows exist on success only (F0), so the surface's dead options (F2) leave no trace at any layer.
