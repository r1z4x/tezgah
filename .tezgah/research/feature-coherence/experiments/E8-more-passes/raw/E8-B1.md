## 2. Objective: one measurable outcome and its Goal → Signal → Metric chain

Goal: *the platform owner can grant and revoke platform-administrator access without
leaving an account that cannot sign in or an account that should have lost access.*

| Rung | Value | Status |
|---|---|---|
| Goal | no orphaned access grant, no un-actionable invite | stated, not instrumented |
| Signal | an invited person reaches first sign-in; a deactivation takes effect | needs the credential-delivery event (F3) and the pending state (F4) |
| Metric | invited-admins reaching first sign-in within 7 days / admins invited in the same 7-day window (ratio, definition = first `refresh_session` row for an invited user, window = rolling 7 days) | **does not exist** — R1, R2 |

Checked against the rubric's rule: a metric with no goal above it is dropped. Here the goal
exists and the metric does not; nothing below the Goal rung is measured today.

## 10. Recommendations, each with its reference

1. **Give the invite a delivery path before selling the button.** Reference: Nembl — "Nembl
   emails them an invitation with a single-use token. They click through, set their
   password, and land in your Company." (`external`, read 2026-09-21). Adopt: a tokenised
   invitation mail reusing the existing `PasswordResetEmailProvider` seam, and the invitee's
   first sign-in as the signal. Owner unnamed in-repo.
2. **Represent the invited state.** Reference: Current's "Pending invitations" list with
   resend and revoke, plus a "Last active" column that reads "Never" for an invite that was
   never accepted (`external`, page updated 2026-09-12, read 2026-09-21). Adopt: write
   `UserStatus.INVITED` at invite time and surface it with a resend action.
3. **Make the roster queried, not filtered in the browser.** Reference: the repo's own
   customers and technical screens (cursor + `q` on the request), which is the strongest
   available standard because it is the product's own convention (`code`).
4. **Stop rendering a sentence where a control belongs.** Reference: Nembl's per-row actions
   ("open detail, deactivate, resend invite") and Current's "Disable member" row panel
   (`external`). Adopt: hide the column when no row can be edited by this account.
5. **Fix the vocabulary.** Reference: the API's own nouns (`/users`, membership, role); the
   screen should not call a platform administrator a team member. `code`.
6. **Instrument or delete the telemetry call sites.** Reference: the repo's own observability
   seam, which supports an enabled client with a real sink (`apps/admin/lib/observability.ts`).

capability-change proposals.

## 11. What this analysis did not look at, and what would change it

- **No user-verbatim evidence at all**: no tickets, interviews, analytics or support corpus
  was available or read. Every value claim here is therefore an inference, not a measurement.
- **One rater.** The rubric requires three to five independent evaluations; this run is one
  pass from two entry points. Severity values are that rater's, and the rubric's own source
  says a single rater is not trustworthy for severity.
- **Data scope: the running dev database.** The platform organisation holds one member and
  one role, so the per-row controls, the confirmation dialog, the error state and every
  non-`ACTIVE` badge could not be rendered. The repo's own e2e fixture provisions a richer
  platform org (`admin-core-recovery.e2e.ts:117-124`), so F2/F6 are *data-condition*
  findings: they hold for a seeded environment and are falsified by a platform org that has
  other roles. Reproducing that fixture would need their suite or a write to their database,
  both outside this run's constraints.
- **Client JavaScript did not execute in the reading browser.** The app's chunks load (29
  `_next/static` resources) but React never attaches (`0` `__react*` keys on `body`, no
  `__next_f`) and the harness refused inline script injection and
  `evaluateOnNewDocument`; the app's own inline RSC payload therefore never ran. So: no
  click-driven dialog open (read through `dialog.showModal()`, the same DOM call the trigger
  makes), no confirmation dialog, no pending/submit state, no live-region announcement, no
  client-side navigation, and the axe sweep ran through `new Function`, not a script tag.
  The repo's own Playwright suite exercises the hydrated app; this limitation is the reading
  environment's, not evidence about the product.
- **Not looked at**: the tenant-side (mobile) user-management surface; the `/users/:id` and
  `/users/:id/deactivate` endpoints as consumers (the panel never calls them —
  `users.controller.ts:49-86`); the audit screen that renders these rows; review mining;
  Core Web Vitals; a 200 % text-size capture; any production data.
- **What would change the recommendations**: a platform org seeded with more than one role
  and more than one member (would move F2/F6 from data-condition to code-condition or clear
  them); a hydrated browser session (would settle U3 and the unreachable component states);
  a real invite delivery path appearing in the codebase (would falsify F3); an owner/team
  map (would fill the owned flag-and-kill-criteria column the triage table leaves unnamed).
