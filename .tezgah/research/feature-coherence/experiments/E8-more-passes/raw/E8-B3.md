## 1. Measurement readiness — the gate

**Finding G1 — `code`, severity 4 (the gate finding).** *The panel's behaviour is not
observable at all: every telemetry call on this surface is a no-op in this build.*

- `apps/admin/lib/observability.ts:22` — `createAdminObservability` sets
  `enabled: options.enabled === true` at `:22`, and `:33`
  `options.enabled ?? new NoopObservabilitySink()`: the default sink is a no-op.
- `apps/admin/lib/observability-runtime.ts:9-12` constructs the client with `environment` and
  `consent` only, so `options.enabled` is `undefined` → `enabled === true` is `false`.
- `apps/admin/lib/observability.ts:36-39` — `defaultAdminObservabilityConsent` returns
  `{ analytics: false, diagnostics: false }`.
- Consequence: `api.request` for `/users` (`lib/api.ts:132-138`) and `recordAdminCrash`
  (`(dashboard)/error.tsx:17`) are emitted into nothing.

So the first finding is not about the screen: **we cannot see this surface yet.** No
invitation-attempt ratio, no invitation-failure ratio, no time-to-invite exists, and no
question of the form "how often does this dead end fire in production" can be answered from the
system as shipped. Everything in §9 about frequency is therefore unmeasured.

**Finding G2 — `code`, severity 2.** *Even with the client enabled, the invite mutation would
not be classified as a create.* `lib/api.ts:46-54` — `classifyCreateEntity` recognises only
`/customers` and `/work-orders`, so `POST /users/invite` emits no `create.started` /
`create.completed` (`:98-103`, `:143-152`). What remains is the generic route id
`api.users.post` (`:41-44`; `users` is in the root allowlist at `:37`), which carries a status
code and a duration but no entity and no outcome for the invitation itself.

## 2. The objective: one measurable outcome, and its chain

No goal statement for this surface exists in the repository. `AdminSurfaceDefinition`
(`lib/admin-surfaces.ts:9-15`) carries `href`, `label`, `disposition`, `group`, `permission` —
there is no purpose or outcome field — and the `/users` entry is four of those five fields
(`:100-107`). The only prose is the page's own description string (`(dashboard)/users/page.tsx:71`
"Panel kullanıcılarını, rollerini ve erişebildikleri kayıtları yönetin.") and the page-level
comment at `:29` ("Roles are organization-scoped…").

The chain below is therefore **proposed**, derived from that string, and named as proposed:

| Step | Value | Evidence class |
|---|---|---|
| Goal | a platform owner manages who can reach the platform business, from the platform panel, without leaving it | derived from `page.tsx:71`, `admin-surfaces.ts:100-107` |
| Signal | an operator attempts a role/scope change and the system records its outcome | *does not exist* — G1 |
| Metric | **invitation-completion ratio** = `POST /users/invite` responses with 2xx ÷ all `POST /users/invite` responses; **and** `access-change-completion ratio` = same over `PATCH /users/{id}`; both per organization per rolling 7 days | not computable — G1, G2 |
| Counter-metric | refusal ratio by code (`SUPER_ADMIN_PROVISIONING_REQUIRED`, `ALREADY_MEMBER`, `ROLE_NOT_FOUND`) | not computable — G1 |

A metric with no goal above it is dropped, and this table has a goal but no instrument: the
honest state is *one proposed ratio, zero available data, and a named reason*.

## 3. Opportunities, and three solutions against a pre-stated criterion

An opportunity is a need, not a feature.

| # | The need | Evidence class | Evidence |
|---|---|---|---|
| O1 | "I need to give a colleague the *least* access that lets them work." | `ui-observed` | the invite dialog's role control offers exactly one option, and it is the highest-privilege role; screen `/users`, invite dialog, `Rol` select, default state |
| O2 | "I need to correct somebody's access after their job changed." | `ui-observed` | the roster's `Yetki güncelle` column renders, and its only row renders a refusal sentence with no control; screen `/users`, roster, row 1 |
| O3 | "I need to know whether my invitation actually went out." | `code` | `(dashboard)/users/actions.ts:70-73` redirects to `/users?result=user-invited` and `lib/api.ts:132-138` would record the call — but the redirect is unreachable for the only role the form offers, and the recorder is disabled (G1) |

**Criterion, stated before comparing**: *the operator completes the task on this screen, unaided,
in one pass; and when the system cannot comply, it says why and offers the next step.*

| Solution | Meets the criterion? | Blast radius |
|---|---|---|
| S1 — filter the role list to the keys the invite path accepts, server-side, and surface that set with the list | yes for O1 | one service method + one DTO; every caller of `listRoles` is affected (`users.controller.ts:40-46` documents the panel as the only caller) |
| S2 — keep the list, disable the offending `option` in the panel so it cannot be selected, and rely on the action's message when it is | partly: the field still shows a choice that cannot be taken | panel-only; leaves two rules that disagree |
| S3 — remove the invite form for the platform organization and link to the documented provisioning flow instead | yes for the surface, no for O1 (the panel then cannot invite at all) | the panel loses its only create action on this screen |

S1 is the recommendation (§10). S2 is what the code almost does today (`actions.ts:61` refuses
after the fact) and is why the defect fires 100% of the time rather than occasionally.

### Findings at their level

All severities are `frequency × impact × persistence` on the rubric's 0-4 scale, and each says
whether it is a **failure** (reproducible, an assertion or a measurement) or a **judgement**.

**U1 — flow/step, `ui-observed`, severity 4, `failure`.** *The invite flow cannot succeed on the
platform organization.* Reproduced live: the invite dialog's role control offers exactly one
option — measured `select[name=roleKey].options` = `["SUPER_ADMIN"]`, its `value` =
`"SUPER_ADMIN"` — filling valid values (`Ad` "Test Davet", `E-posta`
`b3-probe-noreply@example.invalid`) passes the browser's own validation (`form.checkValidity()
=== true`), the confirmation dialog lists `Rol: Platform sahibi`, and confirming returns an
in-dialog `role=alert` reading "Platform sahibi bu ekrandan atanamaz." The roster still held
1 row afterwards. The path is deterministic, so this is 1/1 by construction, not a sampled
rate. Screen: `/users`, invite dialog, `error` state.

**U2 — screen, `ui-observed`, severity 3, `failure`.** (the implementation side is the
citation at `page.tsx:205-206`; the class is the live read.) *The column that promises the
action is present for 100% of the rows and actionable for 0% of them.* `page.tsx:205-206`
renders, for a `SUPER_ADMIN` membership, a `<p class="muted">` sentence and no control; the
organization has exactly one member (the platform owner), so every row takes that branch. Read
from the clean 1440 capture: *the header promises an action ("Yetki güncelle") but the cell
contains a non-interactive, grayed explanation.*

**U3 — property, `ui-observed`, severity 3, `failure` (measured).** *At 1440 CSS px — the
app's own baseline width — the last column is clipped and there is no visible affordance that
more exists.* Measured on the live page: `.tableWrap` `clientWidth` **1084**, `scrollWidth`
**1140** → **56 px** hidden, **4.9%** of the table; the `Yetki güncelle` header's right edge is
**1443** against the region's right edge **1387** → `clippedPx` **56**, and the same 56 px on
its data cell, so the sentence in row 1 is cut mid-`değiştir`. `scrollHeight − clientHeight` of
the scroll region is **0**, i.e. the overflow is horizontal only and macOS overlay scrollbars
paint nothing at rest. Cause, cited on both sides: `app/globals.css:561-566` (`.tableWrap
{ overflow-x: auto }`, `table { width: 100% }`) with `app/globals.css:568-573`
(`th, td { white-space: nowrap }`), so the table's min-content width wins over its container.
At the other breakpoints, measured: **768** — `clientWidth` 686 / `scrollWidth` 1140, and
`Kapsam`, `Üyelik`, `Yetki güncelle` are **entirely** off-region (3 of 7 columns); **320** —
`clientWidth` **242** / `scrollWidth` 1140, **78.8%** hidden; **200% root text at 1440** —
`clientWidth` 1084 / `scrollWidth` **1943**, **44.2%** hidden.

**U4 — component, `ui-observed`, severity 2, `failure`.** *A failed invite is not recoverable
from the dialog and its failure is re-shown on reopen.* Live: after the U1 failure, pressing
Escape and re-opening the modal renders the same `.adminFormFeedback.error` with
"Platform sahibi bu ekrandan atanamaz." before any action is taken in that session, and the
previous values (`Test Davet` / `b3-probe-noreply@example.invalid`) are still in the fields —
the form is not reset on close, so a stale error is presented as if it belonged to a fresh open.

**U5 — component, `ui-observed`, severity 2, `judgement` (2 passes).** *The dead end is
presented with no next step.* The image pass on the failure capture: *"None is provided. The
error states what is not allowed but offers no instruction (e.g. 'select a different role')."*
Neither pass found a route out — the only remaining role is the rejected one. Heuristic 9.

**U6 — screen, `ui-observed`, severity 2, `failure`.** *The screen renders an error namespace it
does not own.* `GET /users?error=registration-submit-failed` renders
`<div class="notice noticeError" role="alert">Başvuru gönderilemedi. Lütfen yeniden deneyin.</div>`
on the team-users screen, because `components/MutationNotice.tsx:12-22` is one global
code→copy dictionary with no per-surface scoping. Reachability is honest: no flow on this
screen redirects with `?error=` (`actions.ts` returns `{ error }`, it does not redirect), so
this is reachable only by hand-editing the URL. It is a wiring defect with low real frequency.

**U7 — component, `ui-observed`, severity 2, `judgement` (2 passes: view tree + image).** *The modal
takes focus to the close button on open.* `document.activeElement` after opening is the element
labelled "Pencereyi kapat" (`components/AdminModal.tsx:156-160`), and the image pass
independently read a visible focus ring on the ✕ in the header. Not a WCAG failure
(2.4.3 is satisfied — focus moves into the dialog); it is H3-adjacent: an accidental Enter or
Space on the way in dismisses the form. Not measured for `:focus-visible` behaviour.

**U8 — property, `ui-observed`, severity 2, `judgement` (1 pass, measured).** *19 tab stops
precede the data region.* Measured focus order over visible, focusable elements: skip link,
brand, 13 nav links, `Çıkış`, the invite trigger, `q`, `Üyelik durumu`, `Filtrele`, `Filtreleri
temizle`, then the `role=region` table (the 20th stop). The sidebar is a legitimate part of the
order; the count is reported because it is a property of a data screen and was not tuned.

**U9 — screen, `ui-observed`, severity 1, `judgement`.** *Two empty states are one state.*
`?q=zzzzz` and `?state=inactive` render the identical block
`Eşleşen kullanıcı yok. Filtreleri temizleyin veya yeni takım üyesi davet edin.`
(`page.tsx:287-291`). An organization with no members at all is not distinguished from a
filter that matched nothing. Unreachable on this corpus (the platform organization always holds
its owner), so the impact is prospective.

**U10 — property, `ui-observed`, severity 1, `judgement` (1 pass, measured).** *One row carries
two status signals with three treatments.* `Durum` renders `<span class="badge">Aktif</span>`
(`page.tsx:187-190`) and `Üyelik` renders the plain text `Aktif` (`page.tsx:200`); in code
the badge has exactly two treatments for five statuses — `badgeWarn` for everything that is not
`ACTIVE` (`page.tsx:186` against `user-labels.ts:16-22`, which defines `ACTIVE`, `INVITED`,
`SUSPENDED`, `DEACTIVATED`, `DELETED`), so four distinct states share one visual treatment and
differ by text only. Only `ACTIVE` was observable on this corpus.

### The imagery, and the two tests

Eight captures were written and **read** (the paths are the evidence; the image bytes were never
inlined): `users-1440-clean`, `users-1280`, `users-768`, `users-320`, `users-1440-dark`,
`users-invite-modal`, `users-invite-confirm`, `users-invite-error`, `users-200pct`,
`users-longtext`, `users-1440-blur`, `users-1440-gray`, `users-768-full`. What the tree could
not answer and the images did: visual hierarchy, the weight of the sidebar against the content,
the toolbar's alignment, whether the two raster actions read as equal, and the colour of the
error box.

- **Blur test** (5 px blur applied to `main`, captured, read): the full-width green
  `Takım üyesi davet et` bar is the strongest mass in the content column and survives as a
  button; the **dark sidebar is the heaviest mass on the page and the content column does not
  beat it**; the weakest masses are the count line and the table's `th`/`td` text, which
  dissolve first. Both passes agree that the primary action is reachable by glance and that the
  page's first read is navigation, not the task.
- **Grayscale test** (`filter: grayscale(1)`): the primary action survives — its primacy is
  carried by fill, size and isolation, not by hue. What degrades: `Filtrele` and
  `Filtreleri temizle` become indistinguishable as two identical outlined buttons, and the
  active nav pill loses its brand accent but not its lightness contrast. Status meaning does
  **not** depend on colour (`AU10`), so nothing is lost there.
- **Dark mode** (`prefers-color-scheme: dark`): the theme is deliberate and complete
  (`app/globals.css:86-116`, `.shell:not([data-theme='light' i])`), and every text/background pair
  measured **7.6 : 1 or better** — so the two image-pass-style worries here are unfounded. One
  oddity: `<body>` stays `rgb(247,248,246)` while `.shell` is `#0c1210`; at every width checked
  the shell covers the viewport, so nothing light is visible, and this is not reported as a
  finding.
- **What nothing read**: focus order, `aria-live` politeness, and the confirmation dialog's
  animation are not image-visible; they were read from the tree only.

### axe-core sweep, and its limits

`axe-core@4.10.2`, pinned and written to disk before injection
(`/tmp/ustam-b3/axe-4.10.2.min.js`, the version read back off `window.axe.version`), run with
`runOnly: { type: "tag", values: ["wcag2a","wcag2aa","wcag21a","wcag21aa","wcag22aa","best-practice"] }`
on `/users`, 1440, light, default state: **0 violations, 47 passes, 1 incomplete
(`color-contrast`)**.

- The injection needed `new Function(source)()` in the page; a plain `<script>` append and
  `page.addScriptTag` both left `window.axe` undefined. Recorded so the next pass does not
  repeat it.
- axe's own documentation puts automated coverage at about **57% of WCAG issues**, so the sweep
  is a floor. The checks it does not make were hand-checked here: **target size** (WCAG 2.2
  SC 2.5.8) — every interactive element in `main` measured ≥ 24×24 CSS px, **pass**;
  **contrast** — the `incomplete` item, hand-measured as nine resolved foreground/background
  pairs in the page, minimum **5.47 : 1** (`.pageHeader .muted`, `rgb(96,103,95)` on
  `rgb(247,248,246)`), **pass at AA**; **focus appearance** — `:focus-visible` matched with a
  3 px solid outline, not measured against SC 2.4.11/2.4.13's area and contrast thresholds,
  **not checked**.

### The WCAG 2.2 level claimed

**AA for the states checked, with no violation found.** The two overflow findings are not
claimed as WCAG failures, and the reasoning is stated so it can be contested: at 320 CSS px
`document.documentElement.scrollWidth === clientWidth === 320`, so the page itself does not
scroll in two dimensions (SC 1.4.10 Reflow is satisfied at the page level), and the table keeps
its own scroll region with `tabIndex=0`, `role="region"`, `aria-label="Kullanıcı listesi"`
(`page.tsx:167`); at 200% root text the nav and the table stay recoverable through
`overflow: auto` (`navBox clientHeight 777 / scrollHeight 790`), so nothing is clipped beyond
recovery (SC 1.4.4). What is **not** covered and not claimed: SC 2.4.11/2.4.13 (focus
appearance), SC 1.3.5 (input purpose), SC 3.3.7 (redundant entry, AA in 2.2 — the invite form
asks for a name and an email that the person owns, not data previously entered by the same
user).

## 6. Feasibility: intended vs implemented

Each row cites both sides. A gap is a finding only when both are cited.

**F6 — `code`, severity 3.** *The panel relays a role list whose only member the invite path
rejects.*

- Documented intent — `(dashboard)/users/page.tsx:32`: *"Roles are organization-scoped: the panel
  offers only the keys the server says are assignable."*
- What the server says — `apps/api/src/users/users.controller.ts:40-46` documents `/users/roles`
  as *"davet formunun rol listesidir"* (the invite form's role list), served by
  `users.service.ts:68-74` `listRoles`, which returns every role **defined in the caller's
  organization** (`where: { organizationId: auth.organizationId }`). Its own docblock calls
  this set the one *"Invitation and access updates resolve roles by organization, so the panel
  lists the same set."*
- What the invite path accepts — `users.service.ts:335-337` `assertGenericRoleAssignment`
  refuses `SUPER_ADMIN` via `superAdminProvisioningOnly()`, throwing
  `SUPER_ADMIN_PROVISIONING_REQUIRED` (`:344-348`).
- So "assignable" is asserted in one place and denied in another, and the panel faithfully
  lists the set that the invite path will not take. The live read is the proof: the platform

## Method notes, for the next pass

- **Browse via `http://localhost:3000`, never `127.0.0.1`.** Next 16's dev server rejects an
  asset request carrying `Origin: http://127.0.0.1:3000` with **403** (verified: the same URL
  with that header returns 403, with a `Referer` header returns 200). Loading the panel from the
  `127.0.0.1` origin leaves the page unhydrated, the client components dead, and the login form
  falling back to a native GET — a session that reads as a broken app.

  sign-in path.

  later navigation lands on `/login`.
- axe-core must be injected with `new Function(source)()` inside the page; a `<script>` append
